## 0. 方案摘要

### 0.1 六个设计决策一览

| # | 决策 | 落地方式 | 依据 |
|---|---|---|---|
| 1 | **步骤边界拆分**：浏览器动作要从「决策」步骤里拿出来 | `runner.py` 的 `_tick_once()` 拆成 predict / act 两段，各自成步骤 | 实测：12 个「执行」步骤共 **8 ms**、12 个「决策」步骤共 **23,006 ms**——动作实际发生在决策步骤内（分析报告 §1.4） |
| 2 | **决策步骤显示传入参数** | 参数表（公开 API）+ 完整请求体附件；**输出侧**才用事后补的私有路径 | 分析报告 §2.3：三条载体路线全部实测过 |
| 3 | **执行步骤显示请求参数与返回值** | 同上；另需库侧接收 `browser.act()` 的返回值并补进 `history` | `agent.py:117` 现在丢弃了返回值 |
| 4 | **录屏三档开关** | `0` 不记录 / `1` 全部（默认）/ `-1` 仅失败；**`-1` 的成功用例不编码、不附加** | 实测：30 秒实录 → **3.5 MB** mp4、编码 **7.15 s**；原始帧 **92 MB/分钟** |
| 5 | **等待独立成步骤（≥200 ms）+ 双开关** | 库侧只记观测值；runner 渲染步骤并**事后改 `start`/`stop`** 拿真实区间 | 实测：事后改步骤时间**生效**（351 ms 真实区间落盘，探针 6） |
| 6 | **二开插件跟框架一起入库 + 版本锁定** | `framework/report_plugin/step-video/` + `scripts/install_report_plugin.py`（幂等 + 版本校验）+ `versions.json` | 实测：`allure.api` 是 CLI 版本相关的扩展点；插件跑通证据见分析报告 §4.4 |

**配置优先级**（决策 1 的答复，沿用仓库既有范式）：

```text
pytest 参数  >  环境变量 JEV_NL_*  >  config.json  >  framework/config.py 内置默认
```

## 2. 改造后的分层与数据流

```text
runner.py（框架层：步骤包装、参数、附件、开关解析）
  │
  ├─ resolve_reports(agent, case, config)          ← 解析四级优先级，得到三个开关的值
  │
  ├─ video.Recorder(agent.browser, mode)           ← 录屏（只读：Page.startScreencast）
  │     └─ 采集线程 drain_events() → artifacts/<case>/frames/NNNNNN.jpg
  │
  ├─ 每轮循环：
  │     ├─ [步骤] 决策        ← predict；参数表 + 请求体附件
  │     ├─ [步骤] 等待         ← 读库记的 last_wait，≥阈值才建（事后改 start/stop）
  │     └─ [步骤] 执行        ← act；参数表 + 请求/返回附件
  │
  ├─ 终局断言 + 终局判定
  │
  └─ video.finish(verdict)                        ← 三档决策：编码/不编码、附加/不附加
        └─ encode.to_mp4(frames, epoch) → allure.attach(..., MP4)
              + allure.dynamic.label("videoEpochMs", epoch)
```

**库侧只增加"可观测性"，不增加"Allure 依赖"**：

| 库侧新增 | 形态 | 为什么不算越界 |
|---|---|---|
| `browser.last_wait` | 一个 dict，记"等了多久、等到没、轮询了几次" | 与 `history` 同类——把发生的事记下来，供上层渲染 |
| `agent.py` history 补 `node`/`role`/`execute_result` | 几个字段 | history 本来就该自包含；与 Allure 无关 |
| `wait_stable` 开关 | 关键字参数，默认 `True` | 默认值保持现有行为不变 |

> **不可越界的那条线**：`agent.py` / `browser.py` **永远不 import allure**。
> 步骤包装、参数、附件全部留在 `framework/`。这条在 AGENTS.md 里已有明文，本方案继续遵守。

## 3. 关键设计一：步骤边界拆分（M1，其余一切的前提）

### 3.1 现状与目标

**现状**（`runner.py:23-42` 的 `_tick_once` 与 `runner.py:98-119`）：

```python
def _tick_once(agent):
    agent.command("predict")                     # ← 决策
    if agent.state["status"] in {"done", "blocked"}:
        return None
    try:
        return agent.command("act", {...})        # ← 执行（同一个步骤体内！）
    except StalePage:
        ...
```

```python
with allure.step(f"第 {steps} 步 · 决策（Jev 概率判断）"):
    _tick_once(agent)                            # predict + act + 页面稳定等待 都在这里
```

**目标**：predict 与 act 各自成为独立步骤，且「执行」步骤**真的包住执行这件事**。

### 3.2 拆分后的循环骨架

⚠️ **`DONE` / `BLOCKED` 必须在查动作表之前分流**（2026-09-24 实施时发现的**方案缺陷**）：
本方案初稿在这里写的是「这个查找不可能失败」，**那是错的**。`DONE`/`BLOCKED` 是通过
`operations.update(DONE=…, BLOCKED=…)`（`model.py:151`）加进**操作字典**的，它们**不是页面元素**；
`model.py:190` 对它们返回的是字面量 `"DONE"`。所以 `next(a for a in page["actions"] …)` 会
**直接 `StopIteration`**。库自己在 `agent.py:93` 就是**先特判、再查表**两条分支——
重写骨架时只抄了后半段，丢掉了前半段。

```python
TERMINAL_CHOICES = frozenset({"DONE", "BLOCKED"})

while agent.state["status"] not in {"done", "blocked"}:
    ...预算检查...

    steps += 1
    before_actions = len(agent.state["history"])

    # ── 决策步骤 ────────────────────────────────────────────────
    ctx = allure.step(f"第 {steps} 步 · 决策（Jev 概率判断）")
    ctx.params = {"步序": steps, "页面": agent.state["page"]["url"],
                  "候选元素数": len(agent.state["page"]["actions"]),
                  "模型": os.environ.get("TYPESAFE_MODEL", "jev-latest")}     # 公开路 1
    with ctx:
        agent.command("predict")
        decision = _latest_decision(agent)
        if decision:
            report_params.fill_decision_outputs(ctx.uuid, decision)            # 事后补（私有）
            attach_decision(decision)
            # ⚠️ 决策附件从此挪到了 act【之前】（原版在 act 之后挂）。
            # 因为附件必须落在决策步骤内，而决策步骤在 act 之前就关闭了。
            # 代价：`act` 与"决策所依据的观察"之间多了一次附件写盘（约 1–3 ms，
            # 相对 400–1900 ms 的模型调用可忽略）。见 §11「M1 遗留问题 2」。
        # DONE/BLOCKED 不产生浏览器动作，但必须调 act 才能把状态落成 done/blocked。
        # 刻意留在【决策】步骤内：给它单开一个「执行」步骤，报告里就会把"什么都没做"
        # 显示成执行了一个动作（§3.3 语义 1）。
        if decision and decision["choice"] in TERMINAL_CHOICES:
            try:
                agent.command("act", {"fingerprint": agent.state["page"]["fingerprint"]})
            except StalePage:
                report_params.mark(ctx.uuid, f"决策 {decision['choice']} 因页面过期被丢弃")
                _reset_after_stale(agent)

    if agent.state["status"] in {"done", "blocked"}:
        break
    if decision is None or decision["choice"] in TERMINAL_CHOICES:
        # 两种"这一轮没有动作"的情形：终止性决策（含被丢弃后重来）、页面过期导致决策被丢弃。
        # 都不建「执行」步骤——建了就会把上一步的动作重复显示成本步的结果。
        continue

    # ── 决策落定、执行之前：抓现场 ──────────────────────────────
    page_before = agent.state["page"]
    selected = decision["choice"]
    # 到这里 selected 一定在动作空间里：DONE/BLOCKED 已在上面的分支里分流掉了，
    # 其余 choice 由 model.choose() 从 controls/targets 的 id 里选出（model.py:185-191）。
    action = next(a for a in page_before["actions"] if a["id"] == selected)

    # ── 执行步骤 ────────────────────────────────────────────────
    ctx = allure.step(f"第 {steps} 步 · 执行 {decision['operation']} → {action['label']}")
    ctx.params = {
        "操作": decision["operation"], "目标索引": decision["target"],
        "元素节点": action["node"], "角色": action["role"],
        "执行前值": action.get("value", ""),
        "是否生成文本": "是" if action["kind"] == "fill" else "否",
    }
    with ctx:
        stale = None
        try:
            agent.command("act", {"fingerprint": page_before["fingerprint"]})
        except StalePage as error:
            stale = error
        # ⚠️ StalePage 有【两种】成因，必须分开报（实施中发现的方案缺陷，实测两种都出现过）：
        #   · history 没长 → 动作确实没落地（act 第一件事就是新鲜度校验）；
        #   · history 长了   → 动作【已经】落地，被打断的是动作之后的 observe
        #     （agent.py:142）。说成"什么都没做"就是把已发生的事报成没发生。
        history = agent.state["history"]
        acted = len(history) > before_actions
        if stale is not None:
            report_params.mark(ctx.uuid,
                "页面已过期，本次执行被丢弃（动作未落地）" if not acted
                else "动作已执行；随后的页面观察失败，本轮以重新观察收尾")
            _reset_after_stale(agent)
            if not acted:
                continue
        # 附件必须在 with 块【内】挂：allure.attach() 挂到当前活跃的步骤上，
        # 出了 with 块就挂到用例上去了（初稿把它写在 with 之外，是错的）。
        attach_execution(agent, action, history[-1])

    # ── 等待步骤：紧跟在产生它的执行步骤【之后】，见 §7.2 ───────
    _emit_wait_steps(agent, steps, threshold_ms)
```

> **原骨架里的 `if len(agent.state["history"]) <= before_actions: continue` 已删除**。
> 它看着像防御性代码，其实是 DONE/BLOCKED 的**唯一**处理路径（终止性决策不追加 history）。
> 分流显式化之后，它成了死代码：走到这一步就必然执行过动作，`history[-1]` 一定存在。

### 3.3 四个必须保住的语义（改错一条报告就是错的）

| # | 语义 | 现状位置 | 拆分后怎么保 |
|---|---|---|---|
| 1 | **`DONE`/`BLOCKED` 不产生动作，不建执行步骤** | `runner.py:106-114` | 用 `TERMINAL_CHOICES` **在查动作表之前显式分流**（见 §3.2 的缺陷说明），终止性决策在决策步骤内落状态后 `continue` |
| 2 | **不把上一步的动作重复显示成本步结果** | `runner.py:110-114` 的注释 | 同一条分流即可保证：走到执行步骤就必然执行过动作。原文的 `before_actions` 快照守卫已退化为死代码，删除 |
| 3 | **`StalePage` 的语义**：丢弃决策 → 重观察 → 状态回 `ready` | `runner.py:34-42` | 抽成 `_reset_after_stale(agent)`，predict 与 act 两侧共用；**两处都要保留** |
| 4 | **步数编号成对** | `runner.py:98/115` 共用 `steps` | 一轮内 `steps` 只自增一次；决策/等待/执行三个步骤共用同一个 `steps` |

**外加一条新增要求（分析报告 §1.4 第 4 点）**：**"决策被丢弃"必须留痕**。
实测 12 次决策只产生 10 条动作，其中第 1 步的决策因页面过期被丢弃，而报告里它与 `DONE` 长得一样。
拆分后要在被丢弃的那一轮**显式记一个附件或参数**，否则"跑了 12 次决策"会被误读成"点了 12 次"。

### 3.4 验收判据（M1 的 Definition of Done）

1. **同一用例拆分前后对比**：逐步骤核对标题、时长、附件数量。
2. **执行步骤的时长不再是 0**（或至少不再是恒为 0–2 ms），且决策步骤的时长**明显下降**。
   用附录 A 第 6 条的命令逐步骤打印时长即可。
3. **步骤数**：一轮循环从 2 个变 2 个（等待未达阈值时）或 3 个（等待达阈值时）。
   `DONE` 那一轮**少一个执行步骤**，与拆分前一致。
4. **丢弃留痕**：能看出"这一轮决策被丢弃了"。
5. `uv run ruff check .` 全绿；`uv run pytest` 离线全绿。

## 4. 关键设计二：步骤参数与附件（M2）

### 4.1 三条参数路线的用法边界

（全在分析报告 §2.3 实测过，这里只定"哪里用哪条"）

| 路线 | 用途 | 限制 |
|---|---|---|
| **路 1**：`allure.step()` 返回的 StepContext，**进入前**设 `.params` | **所有进入前就知道的量**（步序、URL、元素节点、操作、目标索引） | 必须在 `with` **之前**设；进入后再改**无效** |
| **路 4**：`reporter.get_item(uuid)` 事后补 | **只有返回后才知道的量**（选中概率、决策耗时、**重发次数**、浏览器返回值） | 私有 API，**只在这一处用**，全部收口到 `report_params.py` |
| 装饰器 | **不用** | 值会被 `repr()` 加引号（`'CLICK'`），且拿不到输出侧 |

### 4.2 `framework/report_params.py` —— 把私有路径收口成一个文件

### 4.3 决策步骤：补哪些字段

`reporting.attach_decision` 现在只挂 7 个字段，`model.choose()` 返回 **14 个**。本次补齐：

| 去处 | 字段 |
|---|---|
| **参数表**（路 1 + 路 4） | 步序、页面 URL、候选元素数、模型名（路 1）<br>选中操作、目标索引、操作概率、目标概率、置信度、决策耗时ms、**决策重发次数**（路 4） |
| **附件**（完整载荷） | `request`（完整请求体）、`raw_answers`（原始响应）、`operation_probabilities` / `target_probabilities`（全量分布） |

**体积控制**（实测：单次请求体 9–20 KB）：
- 完整请求体挂附件，**不挂 `state.page.text`**（可省一半以上）；

### 4.4 执行步骤：请求参数与返回值

所以"写入文本 / 文本模型耗时"**进不了参数表**，只能进附件。
**不要为了让它进参数表去把文本生成从库里挪出来**——那会改变 `pending_text` 复用与新鲜度校验的既有语义。

### 5.2 ⚠️ 为什么不能放进 `framework/config.py` 的模块级常量

`config.py` 现在是这样读环境变量的：

## 6. 关键设计四：录屏与合成（M5）

### 6.1 录制放在框架层，不动库

`browser.py` 已有一个 `record_dir` 机制（`agent.py:149-152`），但它**每个动作只存一张截图**，
不是连续录屏，不足以合成视频。所以本期的录制**新写一个框架侧组件**，只读地用 CDP：

```python
# framework/video.py
class Recorder:
    """后台标签页的连续录屏。

    只读：Page.startScreencast 是协议级截屏，不碰页面、不碰用户可见标签页。
    与 scripts/record_flights.py 同一套机制（那份已在线跑过），
    差别是把 epoch 锚点与步骤时间戳严格对上。
    """

    def __init__(self, browser, out_dir):
        self.epoch = time.time()          # ← CDP metadata.timestamp 是 Unix 纪元秒，同基准
        browser.call("Page.startScreencast", format="jpeg", quality=80,
                     maxWidth=1120, maxHeight=780, everyNthFrame=2)
        ...采集线程 drain_events()...
```

**实测参数**（分析报告 §4.1）：`everyNthFrame=2` / q80 / 1120×780 → 约 **20 fps**、帧约 **70 KB**。

### 6.2 合成：必须用 `concat + cfr`，不能用固定帧率

```python
# framework/encode.py
def to_mp4(frames, gaps_ms, out_path, fps=30):
    """jpeg 帧 → mp4。

    为什么不用 `-framerate <平均帧率>`：帧间隔是不均匀的（实测中位 33.8 ms、最大 397 ms），
    固定帧率会把误差弄到 中位 85 ms / 最坏 451 ms，"点第 6 步"可能跳到别的画面。
    concat 把每帧真实 duration 喂进去 + `-fps_mode cfr -r 30` 重采样到均匀网格，
    实测降到 中位 17 ms / 最坏 33 ms。见分析报告 §4.2.2。
    """
```

固定参数（**这三个都不能省**）：

| 参数 | 为什么 |
|---|---|
| `-fps_mode cfr -r 30` | 按真实时间戳重采样（对齐精度 ±1 帧） |
| `-pix_fmt yuv420p` | 否则浏览器可能报 "does not support video tag"（Allure issue #1676） |
| `-movflags +faststart` | moov 前置，边下边播 |

### 6.3 三档与清理时序

| 档位 | 启动录制 | 编码 | 附加 | 原始帧 |
|---|---|---|---|---|
| `0` | **否** | — | — | — |
| `1` | 是 | 是 | 是 | 跑完清 |
| `-1` + 通过 | 是 | **否** | **否** | 跑完清 |
| `-1` + 未通过 | 是 | 是 | 是 | 跑完清 |

**两个要点**：

1. **`0` 必须"不启动"，而不是"录了再删"**——否则白付录屏开销（观察阶段 +3–6 ms/次、采集线程持续轮询）。
2. **`-1` + 通过 要"不编码、不附加"，而不是"生成再删"**——Allure 在 `attach()` 时会把字节
   **拷贝**进 `allure-results/`，附加过之后再删原文件也删不掉报告里那份。
   等价的结果，还省掉 **7 秒**编码。

**清理必须放 `finally`**：帧约 **92 MB/分钟**，30 秒用例先落 ~46 MB。
无论成败、无论异常，帧目录都要清（失败的用例留 mp4，不留帧）。

### 6.4 "通过"的判定边界（**这里最容易出事**）

`-1` 会**删证据**，删了追不回。所以"要留"的边界必须画严：

```python
def should_keep(verdict, note, history, snapshot):
    """-1 档下是否保留录屏。

    只有【明确通过】才不保留。下面这些"通过了但不健康"的情况一律保留：
      · 终局判定 ok=False（自然要留）
      · note 非空（达到步数上限 / 超时提前停止）
      · 过程里出现过 StalePage 重决策、或 decision_attempts > 1
      · pytest 的 RERUN（第一次是失败的）
    """
```

理由：这些运行**恰恰最值得看**——通过了但过程不健康，正是下一轮要查的对象。
并且**删除动作必须写进报告**（一条附件或参数："本次按 `-1` 档未保留录屏"），不能静默。

### 6.5 附加到报告

```python
allure.attach(mp4_bytes, "执行录屏", allure.attachment_type.MP4)
allure.dynamic.label("videoEpochMs", str(int(epoch * 1000)))   # ← 必须是 label，不能是 parameter
```

**`label` 不是 `parameter`**（实测，分析报告 §4.2.3）：`parameter` 会改 `historyId`，
于是**每次运行都变成一条新用例**，History/Trend/Retries 全废——**而报告页面看不出任何异常**。

## 7. 关键设计五：等待步骤（M4）

> ### ⚠️ 本节是对可行性报告 §8.5 的一处**归属修正**（2026-09-24 复核时发现）
>
> 可行性报告里写的形态是「在第 N 步的**决策与执行之间**插一个『等待页面稳定』步骤」。
> 复核代码位置后发现**那样会把等待归属到错误的轮次上**：
>
> `browser.py` 里的等待，除了首屏那一次，**其余全部发生在 `act` 内部**
> （`follow_new_tab` 的新标签页稳定等待、`observe()` 的输入后同步等待）。
> 若把等待步骤放在执行**之前**，它显示的是**上一轮 act** 里发生的等待——**错位一轮**，
> 而且报告上完全看不出来（时间区间是真的，只是归属错了）。
>
> **修正后的设计**：等待步骤紧跟在**产生它的执行步骤之后**，用同一个 `steps` 编号，
> 标题写明是哪一类等待。归属正确，且仍然是"独立成步骤"。

### 7.1 库侧：记录**一组**观测值，不 import allure

一次 `act` 里可能发生**不止一次**等待（先 `follow_new_tab` 的稳定等待，再 `observe` 的输入后同步等待），
所以记录必须是**列表、每次 act 前清空**——否则后一次会覆盖前一次，报告里少一个等待。

```python
# browser.py —— 与 Allure 完全无关，只是把"等了多久、等到没"记下来
self.waits = []                    # 本轮动作里发生的所有等待

def _record_wait(self, kind, started, elapsed_ms, **extra):
    self.waits.append({
        "kind": kind,                              # stable / settle / input_sync
        "started_ms": int(started * 1000),         # Unix 纪元毫秒，与 Allure 步骤时间同基准
        "elapsed_ms": elapsed_ms,
        **extra,                                   # stable: 是否等到稳定 / polls / timeout
    })
```

三个记录点，对应 §8.1 里的三处（`kind == "wait"` 的动作不记——它本身就是一个执行步骤）：

| 记录点 | `kind` | 触发场景 |
|---|---|---|
| `Browser.__init__` 的 `wait_until_stable` | `"stable"` | 首屏（E9 上 2–3 s，最大的一笔） |
| `follow_new_tab` 的 `wait_until_stable` | `"stable"` | 点击打开了新标签页（E9 流程表单就是） |
| `observe()` 的 `after_input` 块 | `"input_sync"` | 输入后等控件同步（50 / 200 / 500 ms 三档） |

同时把 `wait_stable` 开关透传进来：

```python
# browser.py
def __init__(self, url, cookies=None, *, wait_stable=True):
    ...
    if wait_stable:
        self.wait_until_stable(timeout=25, interval=0.6)
```

```python
# agent.py
def __init__(self, url, goals, *, cookies=None, record_dir=None, screenshots=False, wait_stable=True):
    self.browser = Browser(url, cookies=cookies, wait_stable=wait_stable)
```

> **这是库公开 API 的扩张**。默认值让现有行为不变，但它是库表面的一部分，
> 评审时要明确——避免下一步有人顺手把 `allure.step` 也加进库里。
>
> **按需记录的代价**：`wait_stable=False` 时**不记**（`waits` 留空），
> 这样报告里不会出现一堆 0 ms 的等待步骤。

### 7.2 runner 侧：≥200 ms 独立成步骤，短等待并进执行步骤的参数

**位置**：紧跟在执行步骤之后，共用同一个 `steps` 编号。

```python
def _emit_wait_steps(agent, steps, threshold_ms):
    """把本轮动作里发生的等待落到报告上。

    门槛 200 ms（已确认的决策）：达到门槛的独立成步骤，短的并进执行步骤的参数。
    理由——每轮都建会塞满 50 ms 级的输入同步等待，报告变流水账、反而看不清重点。
    """
    waits = list(getattr(agent.browser, "waits", ()))
    agent.browser.waits.clear()                     # 消费掉，避免下一轮重复显示

    for wait in waits:
        if wait["elapsed_ms"] < threshold_ms:
            continue
        label = {"stable": "页面稳定", "settle": "文档就绪", "input_sync": "输入后控件同步"}[wait["kind"]]
        ctx = report_params.step(f"第 {steps} 步 · 等待（{label}）", {
            "等待耗时ms": wait["elapsed_ms"],
            "是否等到稳定": wait.get("stable", "不适用"),
            "轮询次数": wait.get("polls", ""),
            "超时上限ms": wait.get("timeout", ""),
        })
        with ctx:
            # 等待发生在库里，runner 包不进 with 块 —— 用事后改时间拿真实区间（§7.3）
            report_params.set_times(ctx.uuid, wait["started_ms"], wait["started_ms"] + wait["elapsed_ms"])

    # 短等待不建步骤，但要并进执行步骤的参数里，否则那点耗时就成了"看不见的成本"
    report_params.fill_outputs(
        <执行步骤的 uuid>, 输入后同步等待ms=..., 标签页稳定等待ms=...
    )
```

**首屏那一次的位置**：它在 `Browser.__init__` 里，循环还没开始。
所以由 runner 在「观察初始页面」**之前**单独取一次，渲染成**前置步骤**
（标题 `前置：等待首屏稳定`），而不是"第 1 步"。归属清晰，也不会污染步数编号。

### 7.3 为什么必须事后改 `start`/`stop` —— 以及 ⚠️ **探针 6 的结论是错的**

等待发生在库里，runner **包不进 `with` 块**——所以步骤时间戳会是"进入/退出"的瞬时值，
又会变成一个 0 ms 的空壳（**正是「执行」步骤那个缺陷的同一成因**）。

> #### ⚠️ 修正：探针 6 说"事后改 start/stop 生效（351 ms 落盘）"——**那是巧合**
>
> 实施 M4 时这条被测试打红了，查清后是这么回事（探针 9 三组实测）：
>
> | | 实测结果 |
> |---|---|
> | **A** | 块内设的 `start` **保住**了；`stop` 被 `stop_step(now())` **覆盖**（2034 → 1790225109251） |
> | **B** | 提前抓住的对象引用**就是**容器里那一份（`is` 判定为真） |
> | **C** | 出块之后再写 `start`/`stop`，**真的落盘**（2034 ms 正确） |
>
> 探针 6 之所以看着成功，是因为它把 `time.sleep(0.35)` 放在 `__exit__` **紧前面**——
> `stop_step` 写的 `now()` 恰好落在真实结束点附近。**数字对上了，机制完全是另一回事。**
> 这正是"把巧合当成验证"的典型：如果当时把 sleep 挪到块中间，立刻就会露馅。
>
> **正确做法是"块内抓对象、块外写时间"**，收口为 `report_params.step_with_real_times()`
> （原方案的 `set_times(uuid, ...)` 按"块内写两个"设计，`stop` 那一半**从构造上就不可能生效**，已删除）。
> 依据是"整个用例的结果到 `close_test` 才序列化"，所以出块后改容器里那份对象仍然有效。

### 7.4 为什么不给库加"等待回调"让 runner 真正包住它

有个更"正统"的做法：`Browser(..., on_wait=callable)`，库在每次等待前后调这个回调，
runner 传一个"开 step / 关 step"的函数进去。这样步骤就是真包住的，不需要事后改时间。

**不采用的理由**：
- 那是把一个**框架形状的钩子**塞进库本体——比"多记一个字段"侵入得多；
- `__init__` 里的首屏等待**没法**用回调包（Agent 构造完它已经过了），仍然要走事后改时间的路；
- 于是两套机制并存，反而更复杂。

**代价**：报告的步骤时间戳依赖 `report_params.set_times()` 这一条私有路径。
它已经被 M2 的单测守住，且只在"等待"这一个场景用。

### 7.5 ⚠️ 这个开关省不了钱，可能反而更贵

**必须在开关的 help 文本和文档里写清楚**：

- `wait_until_stable` 存在的全部理由，是防"渲染中途决策 → 立刻 `StalePage` → 重观察 → 重决策"；
- 而每轮重决策都是**一次付费的 TypeSafe 请求**；
- 它节省的只有那几次**免费**的 `observe()`；
- **所以关掉它 → 决策请求数可能上升 → 批量执行更贵。**

**这个开关的定位是"调试/诊断"，不是"回归省钱"。**
如果目标是省钱，**优先调小 `timeout`（25 s → 8 s）**——超时后一样往下走，
但保留了"稳定就立刻返回"的快路径。

**在 §13 的 A/B 数据出来之前，保持默认开启。**

### 8.6 光标合成与"点一次停住"（封板后补做）

两条需求都来自实际用报告的人，不是分析报告里推出来的。**都不改库本体的语义**。

#### 需求一：点步骤当场停住，再点同一步才继续播

原实现是"跳到 + 立刻 `play()`"。**问题是绝大多数步骤只有 1 秒上下**——
跳过去就开始播，等你看清已经播完了。

| 你的动作 | 结果 |
|---|---|
| 点某一步 | 跳到那一刻并**暂停**（状态行写明"再点这一步继续播放"） |
| **再点同一步**（视频还停在那儿） | 从那一刻继续播 |
| 播放中点任意一步 | 跳过去并**停住**——不是继续播 |

判据是**状态**而不是简单的 toggle：只认"`paused` 且位置没被拖走过"才算"再点一次"，
否则"第三下点同一步"会变成继续播而不是回到那一刻。

#### 需求二：画面上看得见鼠标

**根因**：录屏里本来就没有鼠标。`Page.startScreencast` 截的是渲染器的合成结果，
系统光标由 OS/浏览器 UI 层画，**不在合成器输出里**——不存在"把光标录进去"的选项。

**做法**：按执行步骤记下的坐标**合成**一个光标（大号箭头 + 圆点 + 点击涟漪），
外加可开关的圆形放大镜（3×、168 px，从同一个 `<video>` 抓帧画进 canvas，
与播放进度天然同步——两个 video 对拷会漂移，且暂停时未必停在同一帧）。

坐标是库层新带出来的「操作坐标」，`via` 说清它的来路：

| 动作 | `via` | 含义 |
|---|---|---|
| click / fill | `mouse` | 真的发了 `mousePressed`/`mouseReleased` |
| scroll | `wheel` | `mouseWheel` 用的固定坐标，**没有真实鼠标位置** |
| select | `js` | 直接设 `value`，**压根没发鼠标事件**，这个点是控件位置 |

坐标本身比"真鼠标位置"还真：act 路径是**先 `scrollIntoView`、再用
`elementFromPoint` 做遮挡校验**、通过了才 dispatch，所以它记下的就是真正被点中的那个点。

#### 换算：分母既不能写死，也不能用帧尺寸推断

插件要把视口坐标（1120×780）映射到画面上。**分母是报告里的 `videoViewport` 标签**，
不是写死的 1120，也不是 `video.videoWidth`：

- 帧是 `startScreencast` 按 maxWidth/maxHeight **等比**缩小出来的。等比时"拿帧宽
  当分母"恰好也对——**但一旦缩放不成比例就静默偏**，报告照常打开、毫无提示；
- 所以记原始视口，插件再做一次**比例一致性自查**，不一致直接出红横幅。

另外必须按 `object-fit: contain` 的**内容矩形**算，不能拿元素框当画面：元素框里有居中留的黑边。
（`object-fit` 在插件 CSS 里**显式钉住**，不依赖浏览器默认值——默认值一改就是静默偏移。）

#### ⚠️ 顺带修掉的一个真 bug：「执行步骤」的判据不能靠标题

自检要拿**最后一个执行步骤**比视频时长，而"哪些是执行步骤"原来是按
**标题里有没有"执行"**认的。终局步骤叫「终局：**执行**结果」——名字里也有，
于是被算了进去，而它发生在**录屏结束之后**。

第一次真跑就撞上了：那条差 **0.57 s**，而容差是 **1.0 s**。
也就是说这次没弹（差一点点），换台慢一点的机器就会弹一条**假的**
"录屏没覆盖到最后一个执行步骤"红横幅——**越是慢的机器越会误报**，最难查的那种。

改判据为**结构**：执行步骤都带「操作」参数（runner 在进入步骤**之前**就设好了，
连"页面过期、动作被丢弃"的那些也有），终局/决策/等待都没有。
整份报告一个「操作」都没有时才退回标题判据（很老的数据）。

> 这条**在界面上看不出来**：计数是对的、横幅也没弹，看不出它错在哪。
> 所以验证脚本当场把 test-case JSON 拉下来重数一遍，
> 并把"标题判据会误算哪几个"写进解说里（实测：13 vs 14，多的那个是「终局：记录执行结果」）。

#### 实测（`artifacts/plugin-cursor/`，真浏览器、不调模型）

样本：拿一份真报告，往执行步骤里**注入**「操作坐标」。只有这一个字段是注入的，
录屏、步骤时间轴、附件全是原报告的。

| 判据 | 结果 |
|---|---|
| 点一步 → 暂停 | `paused=true`、`currentTime=1.97`、状态行提示可再点 |
| 再点同一步 → 播放 | `paused=false`、`1.97 → 2.89` |
| 播放中点另一步 → 停住 | `paused=true`、`currentTime=9.53` |
| 光标位置（**独立重算**比对） | 期望 [1159.7, 130.2]，实际 [1159.7, 130.2] |

| 开关、播放高亮、**零 JS 报错** | 全过 |

**21 条断言全过**，**受控样本与真跑出来的报告各跑一遍**（期望值从报告数据里读，
不写死在脚本里，所以同一套断言两边都成立）。另跑了**老报告**（没有操作坐标）的回归：
不报错、叠加层隐藏、开关区如实说明"步骤里没有「操作坐标」"。库侧另有
`scripts/check_guards.py` 的真浏览器断言（不花钱）：`act` 返回的点 == 元素**当前**中心，
且 select 的 `via` 必须是 `js`。

> ⚠️ **测"再点一次开始播放"必须发真鼠标事件**（`Input.dispatchMouseEvent`），
> 不能用合成的 `li.click()`：合成事件不算用户激活，`play()` 会被自动播放策略拒绝，
> 测出来是一个**假失败**。被拒时插件会在状态行说出来，不静默。
>
> 驱动侧还有三个坑（都在 `artifacts/plugin-cursor/drive.py` 里）：
> 后台标签页会把**媒体解码**节流到 `readyState` 恒为 0，要靠
> `Emulation.setFocusEmulationEnabled` 解开（库本体对后台页做的是同一件事）；
> `Page.captureScreenshot` 在后台页可能挂住，截图只能当尽力而为的证据、不能当断言；

> 三个都不是"代码写错"，而是**对机制的假设错了**，而且每一个都只表现为"视频有点短"，
> 不看帧数根本发现不了。
>
> **① 丢帧的真凶是过滤器，不是录屏**（最严重）
> 原实现按 `session_id == browser.session` 过滤帧。但录屏是**绑在 target 上**的：
> 同一个标签页换会话（`_reattach`）时 screencast 继续在跑，帧照样发，只是带着**旧会话 id**
> ——于是切换那一刻之后的帧**全部被丢掉**。实测那条 26 秒的用例因此只有 **5 帧**。
> 改成"接受**所有录过屏的会话**的帧"后，同一条用例拿到 **270 帧**。
> 探针 11 还验了补集：真的换 target（`follow_new_tab`）时**需要**在新会话上重开录屏
> （重开前强制重绘 3 次新增 0 帧，重开后恢复）。
> 顺带：`Screencast is already active` 是**正常情况**（同一标签页换会话），
> 记进 `errors` 会让报告看起来像坏了——已改成不算错误。
>
> **② 视频的 `t=0` 必须对应 `epoch`**
> 第一帧盖住的应是 `[0, t1)`，不是 `[t0, t1)`。按后者编出来的视频 0 秒实际是 `t0`，
> 于是**每一步都偏 `t0`**（从开始录制到第一帧到达的耗时）——实测出现视频 34.07 s、
> 用例 48.57 s 的差。这种"整体偏移一个固定量"最难怀疑：**每步都错，且错得一样多**。
>
> **③ 最后一帧必须保持到录制结束**
> CDP screencast 是**重绘驱动**的（探针 10：空闲 3 秒 **0 帧**；4 次点击只有 2 帧）。
> 帧因此可能只集中在开头几秒。若最后一帧只补一个中位间隔，视频会在用例还没跑完时就结束
> （实测 4.77 s vs 26 s），"点第 12 步"的 seek 会 clamp 到末尾——**跳到完全无关的画面上**。
> 现在把 `end_epoch` 带进合成，视频总时长 == 真实录制跨度。
>
> #### ⚠️ 对可行性报告的一处**量化修正**：帧率是"重绘驱动"的，不是 20 fps
>
> 分析报告 §4.1 记的"约 21.6 fps、帧约 70 KB"是**在连续滚动下**测的——
> 滚动让合成器每帧都提交，所以帧率很高。**真实用例不是这样**：
> 页面在等模型决策时完全静止，一帧都不出。所以真实录屏是**稀疏幻灯片**：
> 视觉变化发生时才有一帧，空闲期由上一帧保持。
>
> **这仍然满足需求 3**：时间轴用每帧的真实时长，seek 到某一刻看到的就是那一刻页面的样子
> ——空闲期画面本来就没变。但有两件事必须说清楚：
>
> - 报告里要能看到**帧数**（已在「录屏说明」里），否则用户会以为录屏坏了；
> - 插件必须把"**步骤发生在录屏范围之外**"和"**对齐错位**"分开报。
>   真实用例里断言与终局判定的步骤就落在录制结束之后（录屏在用例收尾前停，
>   因为那时浏览器已经关了、没什么可录），不能当成错位。
>   **这条留给 M6 的插件实现。**
>
