## 0. 结论摘要

三条需求的可行性差异很大，先给结论：

| 需求 | 可行性 | 关键结论 |
|---|---|---|
| **1. 决策步骤显示传入参数** | ✅ **完全可行，且数据已经就绪** | 完整请求体（`decision["request"]`）与原始响应（`raw_answers`）**已经在内存里**，只是 `reporting.attach_decision` 没挂出来。实测：单次请求体约 **9–20 KB**，12 次决策合计 **0.15–0.3 MB/用例**，挂得起。 |
| **2. 执行步骤显示请求参数与返回值** | ⚠️ **可做，但必须先修一个结构缺陷** | 实测：12 个「执行」步骤总时长 **8 ms**，而 12 个「决策」步骤总时长 **23,006 ms**——**浏览器动作实际发生在决策步骤内部**，执行步骤只是个零宽度的标签。不拆步骤边界，给执行步骤加什么参数都名不副实。 |
| **3. 加录屏 + 步骤↔视频同步** | ✅ **可以做到，且同步精度可控到 33 ms** | 四件事都实测过了：① CDP 后台标签页录屏可行（30 秒实录 → 3.5 MB mp4，编码 7 秒）；② Allure 能**内嵌播放** mp4；③ 步骤时间戳与视频时间戳**同基准（Unix 纪元）**，可直接换算，对齐误差取决于合成方式——固定帧率中位 **85 ms** / 最坏 **451 ms**，改成 `concat + cfr 30` 后降到中位 **17 ms** / 最坏 **33 ms**；④ **二开已写探针插件跑通**：自定义区块渲染进真实用例页，拿到了全部 29 个步骤的绝对时间区间，零 JS 报错。**不需要改 Allure 本体**，只用官方插件 API（`window.allure.api`）。 |

**最需要先知道的一句话**：需求 2 和需求 3 **是耦合的**。当前「执行」步骤是零宽度的（`start == stop`），
而"点第 6 步 → 录屏跳到第 6 步那一刻"必须依赖步骤有真实的时间区间。
所以**需求 2 的步骤边界拆分是需求 3 的前置条件**，两者应当同期做。

**五个开放问题已确认**（配置优先级、录屏三档、保留策略、等待步骤、二开位置与版本锁定），
见 §7；其中"等待做成报告步骤 + 双开关"的完整分析在 §8，"二开的版本锁定"在 §9。
**两处需要实施期补的实测**（本报告没做、也不能靠推断）已列在 §6 末尾。

## 1. 现状剖析：现在的 Allure 报告是怎么生成的

### 1.1 三个环节

```text
pytest 执行
  └─ tests/test_nl_cases.py + conftest.py   把 YAML 用例收集成 pytest 用例
      └─ framework/runner.py:run_case()     逐轮执行，用 allure.step 包步骤、allure.attach 挂附件
          ├─ framework/reporting.py         附件内容（决策概率、截图、执行轨迹、环境信息）
          └─ framework/assertions.py        断言判定与证据
              ↓
      report/allure-results/*-result.json   原始结果（allure-pytest 2.13.5 写的）
              ↓
      allure generate … -o report/allure-report    Allure CLI 2.13.8 渲染成静态 HTML
```

### 1.2 一条用例的步骤骨架

`runner.py:86-168` 决定了报告的骨架，每轮循环产生两个步骤：

```python
with allure.step(f"第 {steps} 步 · 决策（Jev 概率判断）"):
    _tick_once(agent)                      # ← predict 和 act 都在这里面
    attach_decision(decision)

with allure.step(f"第 {steps} 步 · 执行 {operation} → {action}"):
    if last.get("text"): attach(str(last["text"]), "写入的文本")
    if screenshot_every_step: attach_screenshot(page)
```

收尾三个步骤：`终局：记录执行结果`、逐条 `断言：xxx`、`终局判定`。

### 1.3 现在挂了什么

| 步骤 | 现有附件 | 备注 |
|---|---|---|
| 前置：接口登录并注入登录态 | `注入的 Cookie 名称` | 只记名字，值不落盘 |
| 观察初始页面 | `初始页面`（标题+URL） | |
| 第 N 步 · 决策 | `Jev 决策概率`（7 个字段） | **需求 1 说的就是它** |
| 第 N 步 · 执行 | 仅 `TYPE_TEXT` 时有「写入的文本」 | **需求 2 说的就是它** |
| 终局：记录执行结果 | `执行摘要`、`执行轨迹`、`最终页面可见文本` | |
| 断言：xxx | `断言证据` | |
| 终局判定 | `断言汇总`、失败时页面截图 | |

`reporting.attach_decision` 只挂了 7 个字段：

```python
{"operation", "choice", "target", "confidence", "probabilities", "latency_ms", "usage"}
```

而 `model.choose()` 实际返回的决策字典有 **14 个字段**（`model.py:192-208`），**没进报告的有 7 个**：

| 字段 | 内容 | 为什么值得挂 |
|---|---|---|
| `request` | **发给 TypeSafe 的完整请求体** | 需求 1 要的就是它 |

| `operation_probabilities` | 全部候选操作的原始概率 | `probabilities` 只留了最终选中目标那一个，**全量分布看不到** |
| `target_probabilities` | 全部候选目标的原始概率 | 同上 |
| `target_confidence` | 目标分支的置信度 | |
| `decision_attempts` | **本次决策发了几次请求** | >1 表示响应不合法重发过。AGENTS.md 明确要求"重发要看得见，不静默自愈"，但现在**报告里看不到** |
| `model` | 响应里回报的实际模型名 | 环境信息里的 `TYPESAFE_MODEL` 是**配置值**，这里才是**实际用的那个**，二者可能不一致 |

> **这一条是本次分析里最"便宜"的收获**：需求 1 不需要新增任何采集代码，
> 只要把已经在手上的字段挂出去。

### 1.4 ⚠️ 结构性缺陷：「执行」步骤是空壳

拿最近一次真实运行的结果 JSON 逐条统计（复现命令见附录 A）：

```text
     0 ms  前置：接口登录并注入浏览器登录态
     1 ms  观察初始页面
  1377 ms  第 1 步 · 决策（Jev 概率判断）
  2396 ms  第 2 步 · 决策（Jev 概率判断）
     0 ms  第 2 步 · 执行 SCROLL_DOWN → Scroll down
  3596 ms  第 3 步 · 决策（Jev 概率判断）
     1 ms  第 3 步 · 执行 CLICK → 进入官网
  …
  4192 ms  第 10 步 · 决策（Jev 概率判断）
     2 ms  第 10 步 · 执行 TYPE_TEXT → 请输入关键词检索更多案例
  …
─────────────────────────────────────────
决策步骤总时长: 23006 ms        （占用例总时长 29488 ms 的 78%）
执行步骤总时长:     8 ms        （0.03%）
```

**结论（【实测】）**：

1. **执行步骤的 `start == stop`**，时长恒为 0–2 ms。它不是"执行"这一步的计时，而是"上一步执行完之后"的一个瞬时点。
2. **真实耗时全在决策步骤里**。`_tick_once()` 在 `决策` 步骤体内同时做了三件事：
   - TypeSafe 决策请求 —— 实测 **中位 393 ms**（10 次：375/554/523/388/382/398/375/539/411/376）
   - **浏览器动作执行**（点击/输入/滚动）
   - 执行后的重新观察 + 页面稳定等待

   也就是说：一次 1.4 秒的「决策」步骤里，**模型只占 0.4 秒，剩下 1 秒是浏览器的事**。
   报告把后者记在了"决策"头上，这才是这个缺陷最误导人的地方。

   逐步耗时（按 `history` 的 `executed_ms` / `elapsed_ms` 增量，【实测】）：

   ```text
   步  操作          执行完成(+ms)   含执行后观察(+ms)
    1  SCROLL_DOWN       3666            3770      ← 首屏稳定等待占大头
    2  CLICK              3554            3597
    3  CLICK              1346            1473
    …
    9  TYPE_TEXT          4117            4192      ← 其中文本模型调用 3328 ms（占 79%）
   10  CLICK              1142            1407
   ```

3. 12 个执行步骤里有 **11 个 `attach=0`**——除了 `TYPE_TEXT` 那一步挂了「写入的文本」，其余什么都没挂。这就是需求 2 看到的现象。
4. **还有一个连带发现**：12 次决策只产生了 10 条动作记录，报告里有 **2 个「决策」步骤没有配对的「执行」步骤**——
   一个是最后一次（`DONE`，本就不该有动作，正常），**另一个是第 1 步**。
   按 `_tick_once` 的分支推断（【推断】），第 1 步的决策是因为 `StalePage`（首屏还在渲染，页面已变）被**丢弃**了。
   但报告里**看不出这个区别**："决策了但被丢弃"和"决策了是 DONE"长得一模一样。这是需求 2 顺带应当补上的可观测性缺口。

**这条缺陷同时打中两个需求**：需求 2 要"给执行步骤加参数"，得先让执行步骤真的**包住执行这件事**；
需求 3 要"点步骤跳视频"，零宽度的步骤没有区间，跳无可跳。

> 值得说明：`runner.py:23-28` 的注释已经写明"刻意不直接调用 `command('tick')`，那样预测与动作会落在同一个 Allure 步骤里"。
> **意图是对的，但实现没落实**——`_tick_once()` 内部仍然把 predict 和 act 串在一起了。
> 这是一个"注释与代码不一致"的缺陷，不是设计分歧。

## 2. 需求一：决策步骤补上「传入参数」

### 2.1 需求澄清

原话："决策步骤有详细的决策返回参数，但没有决策执行方法的传入参数，你帮我看下能加上决策的传参也一并加上 allure 装饰器，显示对应的传参吗"

拆成两件事：

- **要显示什么**：发给 TypeSafe 的请求参数（目标、上下文、候选元素表、指令），以及原始响应。
- **用什么载体显示**：原话提到"allure 装饰器"。

### 2.2 载体选型（三种都实测过）

Allure 的步骤能承载两类东西，本次把三种写法都跑了一遍确认渲染效果：

| 载体 | 写法 | 实测渲染结果 | 适合 |
|---|---|---|---|
| **A. 步骤参数** | 构造带 `params` 的步骤 | 折叠行显示 **"3 parameters"** 徽标，展开是**参数名/值表格** | 短、结构化、想一眼扫到的 |
| **B. 附件** | `allure.attach(json, name, JSON)` | 折叠行显示 **"1 attachment"**，点开查看器看全文 | 长、大、非结构化 |
| **C. 标题内联** | 把参数拼进 `allure.step(title)` | 直接显示在步骤名里 | 一两个关键值 |

实测原始输出（复现见附录 A）：

```text
A 载体：StepContext(params) 3 parameters, 0s
    操作 CLICK    目标索引 3    概率 0.93
B 载体：attach(JSON) 1 attachment, 1ms
    决策请求参数 66 B
C 载体：标题内联 · CLICK → [3] p=0.93 0s
```

**关于"allure 装饰器"**：`@allure.step` 装饰器**做不到**这里的需求。它的参数来自被装饰函数的**入参**
（`allure_commons._allure.StepContext.__call__` 里 `params = func_parameters(func, *a, **kw)`），
而决策的**输出**（选了哪个操作、概率多少、重发了几次）不在入参里，是调用之后才知道的。所以装饰器只能给"输入侧"。

### 2.3 步骤参数怎么填：三条路，全部实测过

**先说机制**：步骤参数是在 `start_step` 那一刻**一次性读走**的，
所以 `allure.step(title)` 这个公开 API 默认给的是空参数。围绕这个机制，实测了三条填补路径。

**路 1：`allure.step()` + 进入前设 `.params` —— ⭐ 推荐，100% 公开 API**

`allure.step(title)` 返回的就是 `StepContext` 对象，在 `with` **之前**给它设 `params` 即可：

```python
ctx = allure.step("第 1 步 · 执行 CLICK → 进入官网")     # 公开 API
ctx.params = {"操作": "CLICK", "目标索引": "3", "元素节点": 42, "概率": 0.93}
with ctx:
    ...
```

实测落盘：

```json
{"name": "第 1 步 · 执行 CLICK → 进入官网", "status": "passed",
 "parameters": [{"name": "操作", "value": "CLICK"},
                {"name": "目标索引", "value": "3"},
                {"name": "元素节点", "value": 42},
                {"name": "概率", "value": 0.93}]}
```

**值保持原样**（不打引号、数字仍是数字）。缺点是 `allure.step()` 的类型标注是宽泛的 `object`，
静态检查会报 `params is unknown`，需要一行类型忽略或一个小包装函数。

**路 2：`@allure.step` 装饰器 —— 可用，但值会被 repr 加工**

装饰器会自动把被装饰函数的**具名入参**取出来当参数（`StepContext.__call__` 里的 `func_parameters`）：

```python
@allure.step("执行 {operation} → {label}")
def execute(operation, label, kind, node, value=""):
    ...

execute(operation="CLICK", label="进入官网", kind="click", node=42, value="")
```

实测落盘：

```json
{"name": "执行 'CLICK' → '进入官网'",
 "parameters": [{"name": "operation", "value": "'CLICK'"}, {"name": "label", "value": "'进入官网'"},
                {"name": "kind", "value": "'click'"}, {"name": "node", "value": "42"},
                {"name": "value", "value": "''"}]}
```

**注意**：值经过 `represent()`，字符串会**带上引号**（`'CLICK'`），标题里也会带
（`执行 'CLICK' → '进入官网'`）。功能上没问题，观感上不如路 1。
**而且装饰器只能看到入参**——决策的输出（选了哪个、概率多少）不在入参里，装饰器拿不到。

**路 3：进入之后改 `.params` —— ❌ 无效（实测反向确认）**

这条是必须知道的坑：`params` 只在 `__enter__` 那一刻被读走，
**进 `with` 之后再改 `ctx.params` 不会被记进报告**。实测断言：进入前设的 `{"进时": "A"}` 有，
进入后加的 `{"事后加的": "B"}` 没有。

**路 4：事后补步骤对象 —— 输出侧唯一的路，但依赖私有 API**

输出侧的量（选中操作、概率、**重发次数**）只有请求返回后才有，只能事后往步骤对象里塞：

```python
ctx = allure.step("第 1 步 · 决策")
ctx.params = {"步序": 1, "候选元素数": 20}       # 输入侧走公开路线
with ctx:
    ...请求与决策...
    reporter = pytestconfig.pluginmanager.get_plugin("allure_listener").allure_logger
    step = reporter.get_item(ctx.uuid)            # TestStepResult
    step.parameters.append(Parameter(name="选中操作", value="CLICK"))
    step.parameters.append(Parameter(name="决策重发", value="2"))
```

实测落盘：

```json
{"name": "E 载体：事后补参数", "status": "passed",
 "parameters": [{"name": "已知输入", "value": "before"},
                {"name": "选中操作", "value": "CLICK"},
                {"name": "概率", "value": "0.93"}]}
```

> **诚实标注**：路 4 里 `pluginmanager.get_plugin("allure_listener")` 与 `reporter.get_item()`
> 都**不是 Allure 承诺稳定的公开契约**（插件名 `allure_listener` 是实测查出来的，不是猜的；
> 实测存在两个含 `allure_` 的插件名：`allure_pytest` 与 `allure_listener`，带 `allure_logger` 的是后者）。
> **升级 allure-pytest 时必须重跑这条验证。**
> 好消息是**只有路 4 有这个问题**——路 1/2 是公开 API，可以先把它们用满。

### 2.4 推荐方案

**分两层，各用各的载体**：

| 层 | 内容 | 载体 | 用到哪条路 |
|---|---|---|---|
| **输入参数** | 步序、页面 URL、候选元素数、模型名、目标文本 | **步骤参数** | 路 1（公开） |
| **输出参数** | 选中操作、选中目标索引、操作概率、目标概率、置信度、决策耗时、**重发次数** | **步骤参数** | 路 4（事后补） |
| **完整载荷** | `request`（完整请求体）、`raw_answers`（原始响应）、全量概率分布 | **附件 JSON** | 现有 `attach_decision` |

理由：
- 摘要参数进参数表，**不用点开附件就能扫到**——这才是"显示传参"的价值。
- 完整请求体 9–20 KB（【实测】，见下），做成参数会把参数表撑爆，必须走附件。
- 输入侧优先用公开 API（路 1），把私有 API（路 4）的使用**局限在输出侧那几个字段**上，
  依赖面积最小——将来 Allure 升级时，需要重验的只有这一小块。

**⚠️ 必须遵守的一条规则**：`.params` 要在 `with` **之前**设。进入之后再改无效（§2.3 路 3 实测）。

**体积实测**：拿一期真抓下来的 E9 表单页观察结果（29 个可操作元素）构造真实请求体：

```text
请求体全文 : 9360 B = 9.1 KB
  state.page   :  713 B
  state.elements: 2692 B
  questions    : 5860 B   （2 个问题；单份 instructions 1466 B）
```

【推断】一条 12 步用例挂全量请求体 + 原始响应约 **0.15–0.3 MB**，20 条用例的回归报告约 3–6 MB。
可接受；若嫌大，可以只挂 `questions`（不挂 `state.page.text`），能砍掉一半以上。

## 3. 需求二：执行步骤补上「请求参数与返回值」

### 3.1 现状与缺口

原话："执行没有对应的参数或返回值显示，需要给执行步骤也加上对应的请求参数和返回值显示"

现状（§1.4 已量化）：执行步骤零宽度、11/12 无附件、真实动作发生在决策步骤内部。

### 3.2 要挂什么

**请求参数侧**——`page["actions"]` 里被选中的那个 action 对象（`snapshot.js:73-91` 产出）：

| 字段 | 例 | 含义 |
|---|---|---|
| `node` | `42` | DOM 节点句柄（代码掌握，不是模型产出的选择器） |
| `role` / `label` | `button` / `进入官网` | 可访问角色与名称 |
| `kind` | `click` / `fill` / `scroll` / `select` / `wait` | 动作类型 |
| `value` | `""` | 执行前的值 |
| `checked`/`selected`/`expanded` | `"true"`/`false` | 控件状态 |
| `current_value` | `古都西安` | `select` 的执行前选中项 |
| `delta` | `560` | 滚动的像素量 |
| `text` | `制造` | `TYPE_TEXT` 实际写入的文本（来自文本模型） |

**返回值侧**：

| 内容 | 现在在哪 |
|---|---|
| `{"executed": "<action id>"}` | `browser_operation()` 返回了，但 **`agent.py:117` 丢掉了** |
| `page_changed`（指纹是否变） | `history[-1]` ✅ |
| 执行后 URL | `history[-1]["url"]` ✅ |
| 执行时刻 / 观察完成时刻 | `history[-1]["executed_ms"]` / `elapsed_ms` ✅ |
| 实际发出的 CDP 调用与坐标 | `browser_operation()` 内部的 `Input.dispatchMouseEvent` 参数，**未留痕** |
| 新鲜度校验（`fresh()`）结果 | 只在失败时以 `StalePage` 异常体现 |

### 3.3 必须配套的结构改造：把 predict 与 act 拆开

这是需求 2 的**真正工作量所在**，也是需求 3 的前置条件。

现状 `runner.py:98-119`：

```python
with allure.step(f"第 {steps} 步 · 决策（Jev 概率判断）"):
    _tick_once(agent)          # ← predict + act 都在这里
```

目标结构（**输入侧用公开路 1，见 §2.3**）：

```python
with allure.step(f"第 {steps} 步 · 决策（Jev 概率判断）"):
    ...（同 §2.4：输入参数走公开路 1，输出参数事后补，完整载荷挂附件）...

# 决策落定后、执行之前，抓下"执行请求参数"需要的现场
action, page_before = 取本次决策要执行的那个 action 与页面快照

# 执行步骤：请求参数在进入前就能知道（**除了 TYPE_TEXT 的文本**，见下）
ctx = allure.step(f"第 {steps} 步 · 执行 {operation} → {label}")
ctx.params = {
    "操作": operation, "目标索引": target,
    "元素节点": action["node"], "角色": action["role"],
    "执行前值": action.get("value", ""),
    "是否要生成文本": "是" if action["kind"] == "fill" else "否",
}
with ctx:
    result = agent.command("act", {"fingerprint": page_before["fingerprint"]})
    # 文本、浏览器返回值、执行后状态都只有这里才拿得到 → 只能挂附件
    allure.attach(json.dumps({
        "请求": {"action": action, "text": text},         # 发给浏览器的东西
        "生成文本": {"值": text, "模型": helper, "耗时ms": text_latency_ms},
        "返回": result,                                    # 浏览器回的 {"executed": …}
        "执行后": {"page_changed": …, "url": …, "elapsed_ms": …},
    }, ensure_ascii=False, indent=2), "执行请求与返回", allure.attachment_type.JSON)
```

> **一个容易踩空的地方**：`TYPE_TEXT` 要写的文本是在 **`agent.command("act")` 内部**
> 由文本模型生成的（`agent.py:106-115`），所以执行者**在进入步骤之前根本不知道要写什么**。
> 这意味着"写入的文本"和"文本模型耗时"**进不了参数表**（除非走 §2.3 路 4 事后补），只能挂附件。
> 想让它进参数表就得把文本生成从库里挪出来——**不建议为了报告好看去动库的执行时机**，
> 那会改变 `pending_text` 复用与新鲜度校验的既有语义（`agent.py:107-110`）。
> 同理，"执行后"的三个字段也只有返回之后才有。

**改造要点与坑**（实施时逐条对照，这几条互相咬合，改错一条报告就是错的）：

1. **`DONE`/`BLOCKED` 决策不产生动作**，现在靠 `len(history) <= before_actions` 判断跳过执行步骤——
   拆分后判断点会变，要保证不产生空步骤、也不把上一步的动作重复显示成本步结果（`runner.py:110-114` 的注释就在讲这件事）。
2. **`StalePage` 的处理**。现在 `_tick_once` 内部捕获 `StalePage` 并重置为 `ready`（`runner.py:34-42`）。
   拆分后 predict 与 act 各自可能过期，两条路径都要保留原语义。
3. **`TYPE_TEXT` 的文本生成时机**。文本模型调用在 `agent.command("act")` **内部**（`agent.py:106-115`），
   所以拆开后"执行"步骤会包含一次文本模型调用。实测该步共 **4192 ms，其中文本模型 3328 ms（占 79%）**。
   这**是对的**——它就是执行的一部分——但报告里必须在参数中标出 `text_latency_ms`，
   否则看报告的人会以为"浏览器输入一个词花了 4 秒"。
4. **步数编号**。现在 `steps` 同时喂给两个步骤的标题；拆分后要保证"第 N 步·决策"与"第 N 步·执行"仍然成对、编号一致。

### 3.4 库本体的改动边界（遵守 AGENTS.md）

AGENTS.md 明确：**不要给库本体打 `allure.step` 之类装饰器**，步骤包装放在 `framework/runner.py`。
但下面两处属于**库侧合理改动**，因为它们与 Allure 无关、只是"history 更完整"：

| 改动 | 位置 | 性质 |
|---|---|---|
| 接收 `browser.act()` 的返回值并写入 `history` | `agent.py:117`（现在没接收） | 让 history 如实反映"浏览器回了什么" |
| 在 history 里补上元素标识（`node`/`role`/`value`） | `agent.py:121-141` 的 history 构造 | 让 history 自包含，不依赖已失效的 `page` |

备选（不改库）：全部在 runner 侧读 `agent.state["page"]["actions"]` 现场拼装。
**代价**：runner 必须在 `act` 之前介入（本来也要拆步骤，所以不算额外成本）。
**取舍**：如果只想动框架层，走备选；如果认为"history 应当记录执行的输入输出"是库的固有职责，走前一种。
**建议后者**——理由是 `history` 是快照的一部分，会被 `attach_trace` 整个挂进报告，
缺了元素标识就永远只能看到 `"进入官网"` 而看不到它到底点的是哪个节点。

## 4. 需求三：执行录屏 + 步骤↔视频同步

原话有两问，逐个回答："先分析能否实现加上录屏，再分析如果录屏能加上，那能否实现录屏和现在的截图的执行步骤一一对上，用例点击查询对应的步骤，录屏就对应显示那个步骤的视频进度条位置。"

### 4.1 第一问：能不能加录屏 → **能（实测）**

**录制机制**：CDP 的 `Page.startScreencast`，本项目**已经在用**——
`scripts/record_flights.py` 用 `browser_harness.helpers.drain_events()` 收 `Page.screencastFrame` 事件、
逐帧落盘、事后 ffmpeg 合成。更关键的是：agent 跑在 `Browser` 自己创建的**后台标签页**里
（`browser.py:31` `background=True`），而 **CDP 截屏是协议级的，不依赖操作系统抓屏**，
所以录制**不会抢占用户的可见标签页**。

**实测开销**（12 秒与 27.7 秒两段样本，页面 `https://www.weaver.com.cn/`，1120×780、jpeg q80、`everyNthFrame=2`）：

| 指标 | 12 s 样本 | 27.7 s 样本 |
|---|---|---|
| 帧数 | 137 | 553 |
| 平均帧率 | 21.6 fps | 20.0 fps |
| 帧间隔 中位 / 最大 | 46.3 / 290 ms | 33.8 / 397 ms |
| jpeg 帧 中位大小 | 63 KB | — |
| **合成 mp4 大小** | — | **3.5 MB** |
| 合成 mp4 耗时 | — | **7.15 s** |
| `screencastFrameAck` 平均耗时 | 7.4 ms（最大 80.7） | — |
| 采集线程异常 | 无 | 无 |

对比一下量级：本仓库已有的 `docs/demo.mp4` 是 7.57 秒、1536×1000、30 fps、**420 KB**。
**即 30 秒实录 ≈ 3.5 MB mp4**，一条用例一个视频文件完全可接受。

**Allure 能不能播**：能，且是**内嵌播放器**，不是下载链接。实测渲染出的 DOM：

```html
<video class="attachment__media" controls>
  <source src="data/attachments/5699bfa0637a5d4.mp4" type="video/mp4">
</video>
```

实测 `duration = 3`（与源视频一致）、`readyState = 4`（已缓冲完）、渲染尺寸 320×200 与源一致。

#### 录屏对 agent 速度的影响（实测，两轮反向 A/B）

screencast 每帧要 ack（平均 7.4 ms，最大 80.7 ms），采集线程每 10 ms 轮询一次 IPC，
所以"会不会拖慢 agent"是真问题。测法：同一站点各开全新标签页，一组录、一组不录，
各做 20 次 `Browser.observe()`，比中位数；**两组都跑，两个顺序都测**。

| 顺序 | 不录制 observe 中位 | 录制 observe 中位 | 差 |
|---|---|---|---|
| 先不录、后录 | 38.9 ms | 41.7 ms | **+2.8 ms（+7.2%）** |
| 先录、后不录 | 46.4 ms | 52.3 ms | **+5.9 ms（+12.7%）** |

**两个顺序方向一致：录屏让每次观察慢约 3–6 ms（7%–13%）。**
一条 12 步用例约观察 24 次（每步决策前后各一次），折算**额外开销 0.07–0.14 秒**，
相对 29.5 秒的用例可忽略。

> **必须说明的边界**：这只是**观察阶段的代理指标**，不是端到端对比。
> 端到端还包含动作执行与页面渲染，要真跑一条用例做 A/B 才能测——**本轮没做，也不该由它下结论**。
> 实施期应补这一组（用演示用例跑两次即可，成本约一次付费跑）。

**顺带测出来的一个重要事实**：`Page.captureScreenshot` 有极强的冷启动效应。
两轮实验里，**后跑的那一组截图总是快得多**（不录 3088 ms → 录 167 ms；反向：录 156 ms → 不录 2350 ms），
即"谁第二个跑谁快"。这说明它是**预热效应**，不是录屏带来的好处：

| `Page.captureScreenshot` | 耗时 |
|---|---|
| 冷启动（该页面上的第一次） | **2.3–3.1 s** |
| 预热后 | **0.16 s** |

相差 **15–20 倍**。这正好解释了 `browser.py:19-22` 注释里"实测约 3.3 秒"的来源，
也说明**首次截图的开销绝不能当作稳态开销**——`on_failure.screenshot`、逐步截图这类功能，
第一个步骤的耗时会明显偏高，报告里看到"第 1 步特别慢"不一定是页面重。
**副作用**：开了录屏之后截图管线自然就是热的，反而是截图路径的净收益。

### 4.2 第二问：能不能一一对上 → **能，且精度可控到 33 ms（实测）**

#### 4.2.1 时钟基准问题（这是整个方案的地基）

要对齐，两个时间必须是**同一把尺子**：

- **Allure 步骤时间**：`allure_commons.utils.now()` = `int(round(1000 * time.time()))`，即 **Unix 纪元毫秒**。
- **CDP 帧时间**：`Page.screencastFrame` 事件的 `metadata.timestamp`。文档只说"帧捕获时间（秒）"，
  **没说基准**。现有 `record_flights.py` 假设它是纪元秒（减去 `time.time()` 当偏移），
  但外面套了 `max(0, …)`——**一旦基准假设错了，所有帧都会被夹到 0**，
  于是它们全写进同一个 `000000.jpg` 互相覆盖，看起来像"只录到一帧"而不是"基准搞错了"。
  所以这个假设必须独立验证，不能靠"视频看着是通的"来反推。

**本次实测结论：确实是 Unix 纪元秒。** 12 秒样本里：

```text
首帧 cdp_ts − 本地纪元 = 0.103 s
末帧 cdp_ts − 本地纪元 = 6.397 s      （跨度 6.294 s，墙钟 6.35 s，吻合）
每帧 cdp_ts 与本地接收之差 = 平均 32.4 ms（就是 IPC+编码延迟）
```

**【实测】所以两个时间可以直接换算**：`视频偏移 = 步骤起始时间 − 录制起点纪元`，不需要额外同步协议。

#### 4.2.2 对齐精度（**本次最重要的实测**）

有了共同基准，剩下的问题是：**合成 mp4 时会不会把时间轴弄歪**。
帧间隔是不均匀的（中位 33.8 ms、最大 397 ms、标准差 62 ms），所以合成方式直接决定精度。

判据：**成品 mp4 里第 i 帧出现的位置，与第 i 帧真实发生的位置差多少**——
这就是"点第 6 步跳过去，画面偏多少"。

| 合成方式 | 帧数（视频/抓帧） | 大小 | 对齐误差 中位 | 对齐误差 最大 |
|---|---|---|---|---|
| A. 固定帧率（`-framerate` 平均帧率） | 553 / 553 | 3.57 MB | **85.2 ms** | **451.0 ms** |
| B. 朴素 concat（逐帧 duration） | 530 / 553 | 3.48 MB | 丢 23 帧，无法对齐 | — |
| C1. concat + `-fps_mode passthrough` | 554 / 553 | 3.48 MB | 62.2 ms | 82.5 ms |
| **C2. concat + `-fps_mode cfr -r 30`** | 835 / 553 | 3.50 MB | **17.1 ms** | **33.3 ms** |

**读法**：

- **A 的问题**：把不均匀的抓帧当成均匀分布，误差**随录制变长累积**。5 秒样本时中位 54 ms / 最大 261 ms，
  27.7 秒样本涨到 85 / 451 ms。451 ms 已经超过一次点击本身，"跳到第 6 步"可能跳到第 6 步之前或之后。
- **B 的问题**：输出时基不够细，几毫秒的帧被量化**丢掉**（553→530）。**朴素实现不能选**。
- **C2 是推荐方案**：concat 把每帧的真实 `duration` 喂进去，再用 `-fps_mode cfr -r 30`
  让 ffmpeg 按真实时间戳重采样到均匀网格。任何时刻的视频位置误差 ≤ 一个输出帧，
  实测**中位 17.1 ms、最大 33.3 ms**（30 fps 下一帧就是 33.3 ms）。**体积几乎没变**（3.50 vs 3.57 MB）。
  代价是输出帧数从 553 涨到 835（重复帧填网格），编码耗时略增。

> **也就是说**：需求 3 要的"点第 6 步 → 进度条跳到第 6 步那一刻"，误差可以做到 **≤ 33 ms（约一帧）**，
> 肉眼完全看不出错位。**关键是要用 C2 而不是"设个帧率就完事"。**

#### 4.2.3 还差一步：让步骤"知道"自己在视频里的位置

对齐的算术是：

```text
步骤在视频里的起点 = (allure 步骤的 start 毫秒 − 录制起点纪元毫秒) / 1000
```

要落地必须解决两件事：

1. **录制起点纪元（epoch）要存进报告，而且载体不能随便选**（见下），否则插件无从换算。
2. **步骤必须有真实区间**——回到 §1.4 的结论：**当前执行步骤是零宽度的**。
   所以**需求 2 的拆分是需求 3 的前置条件**，这不是可选项。

#### 载体选型：epoch 绝不能做成 `parameter`（实测的坑）

epoch 每次运行都不同。Allure 用 `historyId` 把同一条用例的多次运行串成 History / Trend / Retries。
本次用三条候选载体各跑两次（纪元取 1000 与 999999）实测：

| 载体 | 写法 | `historyId` 是否被变化的 epoch 影响 | 结论 |
|---|---|---|---|
| **parameter** | `allure.dynamic.parameter("录制起点纪元", epoch)` | ❌ **变了**（`c07b9e0e…` → `244cc28f…`） | **不能用**：每次运行都会变成一条新用例，History/Trend/Retries 全废，**而且报告看起来一切正常** |
| **label** | `allure.dynamic.label("videoEpochMs", epoch)` | ✅ 不变 | **可以用** |
| 附件 | `allure.attach(...)` | ✅ 不变 | 可以用（但插件要多一次读取） |

**推荐用 label**（`allure.dynamic.label("videoEpochMs", <纪元毫秒>)`），理由：
- 实测不影响 `historyId`；
- 落盘形态是 `{"name": "videoEpochMs", "value": "1000"}`，而**插件侧早就把它读出来了**
  （§4.4 的探针插件就是按 `data.labels.filter(l => l.name === 'videoEpochMs')` 取的，
  在真实报告上跑过、无报错）。

> 顺带记录一个 API 名字的坑：**是 `allure.dynamic.parameter`，没有 `allure.parameter`**
> （项目里 `tests/test_nl_cases.py:31-33` 用的就是 `allure.dynamic.*`）。
> `allure.dynamic.label(label_type, *values)` 的第三个位置参数**不是**"是否排除"，
> 传错会让值变成 `False`——本次第一次写就踩到了。

### 4.3 开源调研结论：**没有现成可复用的成品，但有一个可照抄的机制**

调研范围：GitHub REST API / raw.githubusercontent / Sourcegraph 代码搜索 / 官方文档 / PyPI 全量索引，
2026-09-24。证据强度沿用本文口径：**已确认** = 读过源码或文档原文；**实测** = 在浏览器里真跑过。

#### 4.3.1 最重要的结论：零个可直接复用的成品

搜过 `allure video`（81 命中）、`allure pytest video`、`allure screencast`（0）、
`allure report plugin timeline`（0）、`test steps video sync`（2 条且无关），
以及 PyPI 索引里 `video ∩ (pytest|allure|selenium|playwright|robot)` 的全部结果——
**没有任何项目做到"在 Allure 报告里点某个 step → 录屏跳到那一刻"。**

**所以需求 3 必须自己实现。** 但机制有现成的、可以几乎照抄的参考。

#### 4.3.2 唯一做成了这件事的开源实现：Playwright Trace Viewer

（microsoft/playwright，Apache-2.0，源码已逐文件确认）

它内部就是「action 列表 + 时间轴 + 帧条 + 录屏」，选中一个 action，视频就跳到那一刻。
**它的做法可以整体搬到我们 CDP + ffmpeg 的栈上**，核心只有三件事：

**(a) 录制侧：给所有东西盖同一条时钟**
```ts
// tracing.ts:_startScreencastInPage()
const onFrame = (params) => {
  const event = { type: 'screencast-frame', ..., timestamp: monotonicTime() };  // ← 自己盖
```
action 的 `startTime` / `endTime` 与帧的 `timestamp` 是**同一条时钟**，所以对齐就是减法。

> **⚠️ 一个与我们的实现冲突的细节**：Playwright **故意不用 CDP 给的 `metadata.timestamp`**，
> 而在收到帧时自己盖一个单调时钟（源码注释与实现都如此）——理由是 CDP 的时间基
> 「在不同版本/进程间不可靠」。
> **这与我们的实测不矛盾**：我们测的是**事实**（在本机 Chrome 153 上它确实是 Unix 纪元秒，
> 且与本地墙钟差仅 32.4 ms），Playwright 说的是**工程判断**（不该依赖它）。
> **取舍**：用 CDP 时间戳更准（它就是捕获时刻），但绑定了实现细节；
> 自己盖时间戳更稳，但要吃 IPC + 编码延迟（**实测这个延迟平均 32.4 ms、最大 147 ms**）。
> **建议**：仍用 CDP 时间戳（准），但**加一个基准自检**——首帧时间戳与本机纪元之差落在合理区间才用它，
> 否则退化为"收到即盖钟"，并在报告里标注降级。这样两头都不吃亏。

**(b) 查看看侧：seek 的公式（这就是要抄的全部）**
```ts
// videoFrame.tsx
const offset = Math.max(0, (time - startTime) / 1000);
if (Math.abs(video.currentTime - offset) > 0.001) video.currentTime = offset;
// 播放时不强行同步，只在漂移超过阈值时才 resync，让视频跑自己的时钟
```

**(c) 帧条：hover 时取"时间 ≤ 光标的最后一帧"**
```ts
const previewTime = min + (max - min) * previewPoint.x / measure.width;
const frame = frames?.[upperBound(frames, previewTime, timeComparator) - 1];
```
缩略图条带由 `videoThumbnails.ts` 生成：`thumbnailsPerSecond = 2`、`maxThumbnails = 120`
（每 0.5 秒抽一帧）。**这也是"视频封面/章节"最省事的做法**，我们可以直接照搬。

**(d) 一个我们没考虑到的、很关键的做法**
```ts
// useVideoSources：把整段视频读成 Blob URL
// 注释原文："so that the player can seek without range requests"
```
**这解决了一个我们本来会踩的坑**（见 §4.3.4 第 2 条）。

**(e) 可自托管，不依赖外网**：`traceViewer.ts` 用 `HttpServer(libPath('vite','traceViewer'))`，

#### 4.3.4 不可行的路（避免重复踩坑）

1. **`#t=` 媒体片段 URL —— 不可靠，会静默失败（双方结论已对齐，本机复现）**。
   外部调研报的是「无效（`currentTime = 0`）」，我自己复现时却是**有效（`currentTime = 1.5`）**。
   追下去发现**两边都对，差别在文件大小与服务器是否支持 Range**。本机复现数据：

   | 场景 | `#t=` 结果 |
   |---|---|
   | 3.5 MB / 27.8 s 视频，`#t=20`，服务器**不支持 Range**（`python -m http.server`），只缓冲到 10.68 s | **`currentTime = 0`** ❌ 跳不过去 |
   | 11 KB / 3 s 视频，`#t=1.5`，已完整缓冲（`bufferedEnd = duration`） | **`currentTime = 1.5`** ✅ 生效 |

   ⇒ **语法本身有效**（Chrome 认这个 fragment），但**能不能跳过去取决于那一刻目标位置的字节是否可达**：
   文件已被完整缓冲就成功，没缓冲 + 服务器不支持 Range 就**静默停在 0**。
   **结论：`#t=` 不能作为方案**——它的失败是静默的、且取决于部署环境。
   正式方案仍应走 JS 设 `video.currentTime`（可靠、与 Playwright 一致），
   或照 §4.3.2(d) 用 **Blob URL**（全量进内存，seek 必然成功）。

2. **⚠️ 报告必须用支持 HTTP Range 的服务器托管**。
   Allure 官方 issue #1676 / #1757 / #1854 全是"视频放不出来/拖不动"。其中 #1757 的成因是
   托管服务器不支持 Range 请求。**注意：`python -m http.server` 不支持 Range**
   （本次探针就是用它在 `127.0.0.1:8898` 起服务的，短片段能播是因为整个文件被缓冲了）。
   ⇒ 正式交付用 `allure serve`（Java 服务器支持）或 nginx。
   **或者照 §4.3.2(d) 把视频读成 Blob URL**，从根上绕开 Range 问题。

3. **mp4 编码必须是 H.264 / yuv420p**。issue #1676 就是有人用 OpenCV 的 `mp4v` 编码导致
   浏览器报 "Your browser does not support video tag"。本次实测的 `libx264 + yuv420p` 正常
   （`readyState=4`、`duration` 正确）。

4. **HTML 附件里包 `<video>` 绕过限制** —— 机制上 2.13.8 确实把 `text/html` 附件渲染进 `<iframe>`，
   但 issue #1854（Allure 2.20.1，`pr:bug`，无维护者回复）显示实际有人失败且无人解释。
   **结果不明，不当稳妥方案。**

5. **GPL / 平台受限的成品不能碰**：
   - `pytest-record-video`（PyPI）：**GPL-2.0**——本仓库是公开仓库，这是红线；且仅 Linux/X11（`ffmpeg -f x11grab`）。
   - `pytest-failed-screen-record`：pyautogui 录整屏，限 pytest<8，不接 Allure。
   - `qawolf/playwright-video`：**已归档**（2021），且是 Node。

6. **Java 系 Allure 插件生态**：`allure-maven` / `allure-gradle` / `allure-teamcity` /
   `allure-bamboo` / `screen-diff` 都是构建/CI 侧插件，**没有 Python 路径**。

#### 4.3.5 顺便值得抄的两个小技巧

1. **把 action 名称烧进画面**：Playwright 官方视频文档提供了 `show: {actions: {...}}`，
   在录制时把每一步的操作名叠加到画面上。对"看录屏时不用回头对照步骤列表"极有帮助，
   而且我们可以在 ffmpeg 阶段用 `drawtext` 事后叠加（不需要动浏览器）。
2. **`wdio-video-reporter` 的计时思路**（MIT，源码已确认）：
   `-r 10 -i %04d.png -vf "scale=…,setpts=N.0*PTS"` —— 把每条命令的截图复制成固定帧数，
   于是**第 N 步的时间偏移 = 帧号 / 10 × 慢放系数**，**完全不依赖 wall clock**。
   我们走的是"真实时间轴 + CDP 时间戳"，比它准；但如果将来发现 `observe()` 太慢导致帧太少，
   这条"按步复制帧"的路子可以作为兜底（代价是视频与真实时间脱钩）。

### 4.4 二开可行性：**有官方插件 API，不用改 Allure 本体（实测）**

原话问"能否二开给当前的 allure 报告添加执行的录屏"。实测结论是：**能，而且比想象的干净**。

Allure 2 报告是一个静态 SPA（实测技术栈是 **Backbone 1.3.3 + Marionette 3.3.1**，不是 React），
**自带插件机制**。生成出来的报告目录里就有：

```text

  ├── index.html                               ← 就是普通 HTML，几行 <script>

      ├── packages/index.js                    1.9 KB
      ├── screen-diff/index.js                 7.0 KB   ← 与我们要做的事最像的样板
      └── …
```

`index.html` 尾部：

```html
<script src="app.js"></script>
<script src="plugins/behaviors/index.js"></script>
<script src="plugins/packages/index.js"></script>
<script src="plugins/screen-diff/index.js"></script>
```

app.js 里暴露了全局插件 API：

```js
window.allure = {
```

#### 二开的落地方式：两条路，都可行

`allure generate` 是 Java CLI，**Python 侧不能注册插件**。但有两条注入路径：

**路 A：生成后处理（本次已实测跑通）** —— 推荐，零 Java

```python
1. 把自定义插件目录拷进 report/allure-report/plugins/<name>/
2. 往 index.html 的 </body> 之前插一行 <script src="plugins/<name>/index.js"></script>
```

实测脚本：`artifacts/probe-allure/postprocess.py`。
**幂等是硬要求**（报告会反复重新生成）：实测重复执行时能识别出"原本就有"而不重复插入。
脚本最后要校验那行 `<script>` 确实在 `index.html` 里——**别让"插件没装上"变成静默失败**。

**路 B：写一个 Java 报告插件（机制已确认，本次未实测运行）** —— 更"正规"，但要写 Java

Allure 2.13.8 的报告模板 `index.html.ftl` 本来就会展开插件清单：

```ftl
<#list plugins as plugin>
    <#list plugin.jsFiles as jsFile>
    <script src="plugins/${plugin.id}/${jsFile}"></script>
    </#list>
</#list>
```

链路是：`ReportWebPlugin.writePluginsStatic()` → `DefaultPlugin.unpackReportStatic()`
（复制插件目录下的 `static/**`）→ 读 `<plugin>/allure-plugin.yml`（字段含 `jsFiles`/`cssFiles`）。
**加载开关是 JVM 系统属性 `allure.plugins.directory`**，而本机 `allure.bat` 第 85 行确实会把
`%ALLURE_OPTS%` 传给 JVM ⇒ 用 `ALLURE_OPTS=-Dallure.plugins.directory=<目录>` 就能加载自己的插件。

**两条路的取舍**：

| | 路 A 后处理 | 路 B Java 插件 |
|---|---|---|
| 本次是否实测 | ✅ **跑通了**（真实报告上渲染出区块，零 JS 报错） | ❌ 只确认了机制（读了源码与 `allure.bat`），**没编译运行过** |

| 对报告"干净度" | 改了一次 `index.html` | 由 Allure 自己生成那行 `<script>`，更正统 |

**建议走路 A**：它已经被实测证明可行，且不需要引入 Java 构建。
路 B 留作"以后要发布成正式 Allure 插件"时的升级路径。

> 两条路都**没有修改 Allure 本体**，升级 CLI 时只要插件 API 不变就不受影响。
> 风险是 `allure.api` 属于 Allure 2 的扩展点，**跨大版本不保证兼容**——本项目已经把 CLI 钉在 2.13.8
> （见 `allure-pytest` 必须 <2.14 的既有约束），所以这个风险是可控的。

### 4.5 四种实现路线对比

| 路线 | 做法 | 精度 | 工作量 | 风险 |
|---|---|---|---|---|
| **① 每步一段视频** | ffmpeg 按步骤区间切 N 个小 mp4，各自 `attach` 到对应步骤 | 每段内部精确；但"进度条位置"永远从 0 开始 | **低**（纯公开 API，无 JS） | 低。缺点：文件多（12 步 = 12 段）、无法连续播放、满足不了"进度条跳到那个位置"的字面要求 |
| **② 整段 + 二开插件** | 一个 mp4 + 自定义插件做时间轴，点步骤 seek | **≤33 ms**（用 C2 合成） | 中（1 个 JS 插件 + 1 个后处理脚本） | 中：依赖 `allure.api`，需在升级时回归。**后处理已实测跑通** |
| **③ 整段 + 伴侣页面** | 生成一个独立的 `timeline.html`（自带视频+步骤时间轴），从 Allure 附件链过去 | **≤33 ms** | 低-中（一个静态页面，无 JS 框架依赖） | 低。缺点：离开报告界面，不是"在报告里点" |
| **④ 自产 trace.zip + Playwright Trace Viewer** | 按 trace V10 schema 造一个 trace 包（帧 + action 时间戳），挂成附件；用 `npx playwright show-trace` 打开 | 与官方同源，**≤1 帧** | **高**（要复刻 trace 格式与打包） | 中：viewer 可自托管不依赖外网，但**它不在 Allure 报告里**（2.13.8 不认这种附件） |

**推荐 ②**，理由：
- 它才是用户要的形态（"用例点击查询对应的步骤，录屏就对应显示那个步骤的视频进度条位置"）；
- 有官方扩展点和现成样板（`screen-diff`），不是 DOM 硬改；
- **后处理这一环本次已实测跑通**（§4.4：真实报告上渲染出区块、拿到 29 个步骤的时间区间、零 JS 报错）；
- 精度实测可控（33 ms）。

**① 作为降级方案**：如果实施期发现插件 API 有问题，先上 ①（纯 pytest/Allure 公开 API，天级），
交付"点步骤看到那一步的录屏"，然后再迭代到 ②。

**④ 不建议本期内做**，但值得知道它存在：它买到的是"官方 trace viewer 的完整体验"
（action 列表 + 时间轴 + 帧条 + 悬停跳帧，§4.3.2 全部机制），代价是要复刻 trace 的包格式。
**注意它和 ② 不冲突**——可以把 trace 包也能挂上，作为"深度排查"入口。

> **路线 ① 的一个实测细节**：切片**必须重编码**，`-c copy` 不行。
> 实测切 [2.0s, 4.5s]：重编码得到 **精确的 2.500000 s**（耗时 1.13 s）；
> `-c copy` 得到 2.567 s（**差 67 ms**，因为它只能在关键帧上切）。
> 所以 12 步就是 12 次重编码 ≈ 额外 14 秒——能接受，但别指望它是"零成本切片"。

### 4.6 需求三的推荐落地形态（草图）

```text
录制：Browser 建后台标签页后 Page.startScreencast
      → 采集线程 drain_events() 逐帧落盘 artifacts/<case>/frames/NNNNNN.jpg
      → 同时记录 epoch = time.time()（与 CDP metadata.timestamp 同基准）

合成：concat + 每帧真实 duration → ffmpeg -fps_mode cfr -r 30
      → report/allure-results/<uid>-attachment.mp4

报告：allure.attach(video_bytes, "执行录屏", AttachmentType.MP4)      # 实测可播
      + allure.dynamic.label("videoEpochMs", epoch_ms)               # 供插件换算（不是 parameter！）

二开：后处理脚本把 plugins/step-video/index.js 拷进报告 + 改 index.html
      插件用 addTestResultBlock 渲染：左侧步骤列表，右侧 <video>
      · 数据从 this.model.toJSON().testStage 取：
          testStage.steps[i].time.start/stop  → 步骤的绝对时间区间（实测能拿到，29/29）

      · 点步骤 → video.currentTime = Math.max(0, (step.start − epoch_ms)/1000)   # 抄 Playwright
      · video timeupdate → 高亮当前时间所在的步骤
      · fetch 整段视频成 Blob URL 再喂给 <video>   # 抄 Playwright：绕开 Range 限制

```

## 5. 风险点分析

### 5.1 需求一

| 风险 | 等级 | 说明与对策 |
|---|---|---|
| 步骤参数的"事后补"用了非公开契约 | **中** | `pluginmanager.get_plugin("allure_listener")` 与 `reporter.get_item()` 不是承诺稳定的 API。**对策**：私有 API 只用在**输出侧那几个字段**上（输入侧走公开的路 1），把依赖面积压到最小；封装成一个函数（如 `framework/reporting.py: add_step_parameters(step_uuid, **params)`）并配一条 eval；升级 allure-pytest 时先跑它 |
| 误以为"进入之后还能改 params" | **中** | 这个坑很隐蔽：代码看着对、跑起来不报错、报告里就是没有。**对策**：封装成"先设 params 再进 with"的唯一写法，不让调用方直接拿到 `.params` |
| `allure.step()` 的类型标注过宽 | 低 | 返回类型标的是 `object`，pyright/mypy 会报 `params is unknown`。**对策**：一个 3 行的包装函数（返回 `StepContext` 并设好 params），把类型忽略收在一处 |
| 附件体积膨胀 | 低 | 实测单次决策请求体 9–20 KB，12 步约 0.15–0.3 MB/用例。**对策**：只挂 `questions` 不挂 `state.page.text`，可减半 |
| 请求体里可能含敏感信息 | **中** | 请求体里含页面可见文本（可能带业务数据）、元素标签。**对策**：沿用现有约定——cookie/token/密码绝不入附件，并明确"报告目录 `report/` 与 `artifacts/` 都在 gitignore"这条边界不放松 |

### 5.2 需求二

| 风险 | 等级 | 说明与对策 |
|---|---|---|
| **步骤拆分改变既有语义** | **高** | `runner.py` 的过期处理、DONE/BLOCKED 跳过、步数编号、`history` 长度判断**互相咬合**，拆错会让报告出现空步骤或重复动作。**对策**：拆分后必须做**同一用例的前后对比**，逐步骤核对标题、时长、附件数量 |
| 改库本体越界 | 中 | AGENTS.md 禁止给库本体打 Allure 装饰器。让 `agent.py` 接收 `browser.act()` 的返回值是"history 更完整"，不是 Allure 耦合，**但要在评审时明确这条边界**，避免下一步有人顺手把 `allure.step` 加进 `agent.py` |
| 文本模型调用被计入"执行"步骤 | 低 | 实测 `TYPE_TEXT` 那步 4192 ms 里有 3328 ms 是文本模型调用（占 79%）。**对策**：参数里带 `text_latency_ms`，让看报告的人能区分"浏览器慢"和"模型慢" |
| **"决策被丢弃"看不出来** | **中** | 实测 12 次决策只产生 10 条动作，其中第 1 步的决策因页面过期被丢弃（【推断】），但报告里它与"DONE"长得一样。**对策**：拆分步骤时，被 `StalePage` 丢弃的决策要**显式留痕**（一个附件或一个参数），否则"跑了 12 次决策"会被误读成"点了 12 次" |

### 5.3 需求三

| 风险 | 等级 | 说明与对策 |
|---|---|---|
| **录屏拖慢 agent** | **低–中** | 已测（§4.1）：观察阶段 **+3–6 ms/次（+7%–13%）**，折算到一条 12 步用例是 **+0.1 秒**，可忽略。但**这只是观察阶段的代理指标，端到端 A/B 没做**，不能据此声称"端到端无影响"。**对策**：实施期用演示用例补一组开/关对照 |
| 磁盘占用 | 低 | 实测 30 秒实录 = 553 帧 jpeg → mp4 **3.5 MB**。**对策**：mp4 留在 `report/`（gitignore），原始帧落 `artifacts/`（gitignore）并定期清理；**`report/` 跨次累积**，需要时 `rm -rf` |
| 帧丢失 | 中 | 实测抓帧是**尽力而为**：帧间隔最大近 400 ms（页面卡顿时会掉帧）。**对策**：① 报告里标注"实际帧率/最大间隔"，让"这段视频没拍到"可被识别；② 不要把"帧率"当作验收指标 |
| 对齐误差 | 低（已测） | 用 C2 合成后中位 17 ms / 最大 33 ms。**对策**：把合成方式固化进脚本并配 eval，**不要**退化成"设个 `-framerate` 就完事"（那会到 451 ms） |
| **插件 API 兼容性** | 中 | `allure.api` 是 Allure 2 的扩展点，跨大版本不保证。**对策**：CLI 已钉 2.13.8；后处理脚本要**幂等**（重复执行不重复插 script）；升级时回归 |
| 二开后处理被忘记执行 | 中 | `allure generate` 之后忘记跑后处理 → 报告里没有插件页面（静默失败）。**对策**：把后处理并进出报告的命令序列（或包成一条命令），并加一条 eval 断言"报告里确实有插件脚本" |
| 视频与步骤对不上的"假成功" | **高** | 如果 epoch 记错或步骤区间错，插件会**若无其事地跳到一个错的位置**——这比没有同步更糟。**对策**：插件里做**自检**：视频时长与"最后一个步骤的结束时间 − epoch"偏差超过阈值时，在页面上显式报错而不是静默跳转 |
| **epoch 做成 parameter 会悄悄毁掉 History/Trend** | **高（已实测）** | §4.2.3 实测：`parameter` 会改 `historyId`，于是每次运行都成了新用例，**但报告页面看不出任何异常**。**对策**：epoch 只用 `label`（或附件），并在测试里加一条断言守住"同一用例两次运行的 historyId 一致" |
| 插件没装上却静默无感 | 中 | 后处理脚本失败（路径写错、报告被重新生成后忘了跑）时，报告照常能看，只是没有时间轴。**对策**：后处理脚本**自校验**那行 `<script>` 确实进了 `index.html`；出报告的命令序列里把它串成一步 |
| **托管服务器不支持 HTTP Range → 视频拖不动** | **中（已知成因）** | Allure issue #1757 就是这个成因。**本次探针用的 `python -m http.server` 恰好不支持 Range**（短片段能播是因为整个文件被缓冲）。**对策**：正式交付用 `allure serve`（Java 服务器支持）或 nginx；**或照 Playwright 的做法把视频 fetch 成 Blob URL**，从根上绕开 |
| **mp4 编码选错 → 浏览器直接报"不支持 video 标签"** | 中（已知成因） | Allure issue #1676 是有人用 OpenCV 的 `mp4v` 编码。**对策**：固定 `libx264 + yuv420p`（本次实测 `readyState=4`、时长正确），并把这套 ffmpeg 参数固化进脚本 + 配 eval |
| `#t=` 看似能跳、实际**静默跳不动** | 中 | **实测（两场景）**：小文件已完整缓冲时 `#t=` 生效；**大文件 + 服务器不支持 Range 时 `currentTime` 静默停在 0**，没有任何报错。**对策**：不用 URL 片段方案；用 JS 设 `currentTime`，或把视频 fetch 成 Blob URL（全量进内存，seek 必然成功） |

### 5.4 三档录屏开关的风险（对应 §7.2）

| 风险 | 等级 | 说明与对策 |
|---|---|---|
| **`-1` 模式静默删掉本该留的证据** | **高** | "仅保留失败用例"= 跑完删成功的。**但"成功"的判定边界一旦画松，就会删掉真正想看的录屏，而且删了就没法追回。** 典型场景：用例判定通过、但过程里出现了 `StalePage` 重决策或 `decision_attempts > 1`——这些"通过了但不健康"的运行恰恰最值得看。**对策**：①只有**明确 `ok=True`** 才删；超时、提前停止（`达到用例步数上限/超时`）、异常退出、`RERUN` 过、`decision_attempts > 1` 的全部按"要留"处理；②删除动作必须**写进日志/报告**（"本次按 `-1` 未保留录屏"），不能静默；③加一条 eval 覆盖"通过但不健康"的用例 |
| `0` 被实现成"录了再删" | 中 | 白付录屏开销（观察阶段 +3–6 ms/次、采集线程持续轮询）。**对策**：`0` 必须**不启动**录制，见 §7.2 |
| 原始帧目录被遗忘 | 中 | 帧约 **92 MB/分钟**（实测），30 秒用例先落 ~46 MB。**对策**：把帧目录的清理放进 `finally`，无论成败都清；并加一条断言 |

### 5.5 等待开关的风险（对应 §8）

| 风险 | 等级 | 说明与对策 |
|---|---|---|
| **关掉等待反而更贵** | **中（未实测）** | §8.4：`wait_until_stable` 是防"渲染中决策→过期→重决策"的机制，关掉会推高**付费的 TypeSafe 请求数**。**对策**：实施期先做 A/B（比决策请求数），拿数据再定；在拿到数据前保持默认开启；若目标是省钱，**优先调小 `timeout` 而不是关掉** |
| 等待步骤把报告变成流水账 | 中 | 每轮多一个步骤、且大量 50 ms 的短等待没有信息量。**对策**：只把 ≥200 ms 的等待独立成步骤，短的并入所在步骤参数（§8.5） |
| 库公开 API 被框架需求推动扩张 | 中 | `Browser.__init__` / `Agent.__init__` 各加一个 `wait_stable` 开关。默认值保持行为不变，但**这是库表面的一部分**。**对策**：评审时明确这条边界，避免下一步有人顺手把 `allure.step` 也加进库里 |

### 5.6 跨需求的共性风险

1. **"报告变好看"不能牺牲"报告说实话"**。AGENTS.md 的铁律是"示例、README 的说法、原始证据、模型调用次数四者必须一致"。
   加了参数显示之后，**`decision_attempts > 1` 必须显眼**（它是"响应不合法重发过"的信号）；
   `RERUN`、`StalePage` 同样不能在更好看的报告里被淹没。
2. **不要为了方便观看而放宽任何安全校验**。录屏和参数显示都是**只读的观察能力扩张**，
   不得触碰"新鲜度校验""遮挡校验""变更操作绝不重试"这三条。
3. **报告体积与保密**：视频与请求体都进报告，而 `report/`、`artifacts/` 已 gitignore。
   这条边界要**继续保持**，不能因为"以后要归档"就把它挪进受版本管理的目录。

## 6. 建议的实施分期

| 期 | 内容 | 前置 | 交付判据 |
|---|---|---|---|
| **第一期** | 需求 1（决策参数）+ 需求 2 的**步骤拆分** + §8 的**等待步骤与双开关** | 无 | 决策步骤有参数表与请求体附件；执行步骤有真实时长（不再是 0 ms）与请求/返回附件；等待步骤带真实区间；两个开关都能被 pytest 参数覆盖 |
| **第二期** | 需求 3 的**录制与合成**（含 §7.2 的三档开关） | 录制与合成互相独立，可先做 | `1` 全留 / `-1` 仅失败留 / `0` 不录 三档行为正确；跑完产出的 mp4 挂在报告里能播；对齐误差实测 ≤ 1 帧；原始帧目录被清理 |
| **第三期** | 需求 3 的**二开插件**（步骤↔视频时间轴）+ §9 的**版本校验与 eval** | 需第一期（步骤要有真实区间） | 点步骤视频跳到对应位置；视频播放时高亮当前步骤；自检失败时显式报错；版本校验能在失配时**拒绝安装** |
| 备选降级 | 路线 ①（每步一段视频） | 无 | 若第三期受阻，先交付"点步骤看那一步的录屏" |

**为什么把"步骤拆分"放在第一期并且优先**：它是需求 2 的必要条件，也是需求 3 第三期的必要条件；
而且它会改变**所有已有报告**的样式，越早做越好定位回归。

**一期内的两组装改按这个顺序落**，因为它们互相咬合：

```text
① 步骤边界拆分（predict / act 分开）      ← 影响所有已有报告的结构
② 决策步骤：参数表 + 请求体附件
③ 执行步骤：参数表 + 请求/返回附件
④ 等待步骤（库记观测值 + runner 渲染）    ← 依赖 ①，因为它也要"有真实区间"
⑤ 两个开关（config.json / 环境变量 / pytest 参数）
```

**一期内必须补的两组实测**（本报告没做，也不能靠推断）：

1. **录屏的端到端 A/B**：同一用例「开录屏 / 不开录屏」各跑一次，比总耗时与决策请求数。
   §4.1 只测了观察阶段的代理指标（+3–6 ms/次），**不足以支撑"端到端无影响"**。
2. **等待开关的 A/B**：同一用例「开等待 / 关等待」各跑一次，比**决策请求数**（不是比耗时）。
   §8.4 的判断是"关掉可能更贵"，但**没测过**——而这正是决定批量执行要不要关的依据。

## 7. 已确认的设计决策（原「待确认的开放问题」）

| # | 问题 | 决策 |
|---|---|---|
| 1 | 录屏开关放哪一级 | `config.json` 提供默认（默认开启）；**pytest 参数可覆盖**——未传值用配置默认，传了就用传值 |
| 2 | 视频保留策略 | **三档**：`0` 不记录 / `1` 记录全部（**默认**）/ `-1` 仅保留失败用例的录屏。<br>实现取最简形态：**执行时一律录，跑完按结果决定留不留** |

| 4 | 等待是否独立成步骤 | **加**，且**只把 ≥200 ms 的等待独立成步骤**（短的并入所在步骤参数）；并且要能由环境变量 + pytest 参数开关，**默认开启**，批量执行时可关闭（分析见 §8） |

### 7.1 配置优先级：沿用仓库已有的三级链

需求 1 说的"config.json 环境变量默认 + pytest 动态传值"，在本仓库**已经有现成的优先级范式**，
不需要新发明一套：

- `e9_config.py` 已经确立 **环境变量 > config.json**（`E9_BASE_URL` 覆盖 `config.json.base_url`）；
- `config.py` 已经确立 **环境变量 > 内置默认**（`float(os.environ.get("JEV_NL_THRESHOLD", "0.75"))`）。

所以新开关按同一条链走，四级：

```text
pytest 参数  >  环境变量 JEV_NL_*  >  config.json  >  framework/config.py 内置默认
（最高，显式）   （CI 覆盖用）        （本机默认）     （兜底）
```

对应到三个落点：

| 落点 | 现状 | 本期新增 |
|---|---|---|
| `tests/conftest.py:pytest_addoption` | `--cases-dir` / `--case` / `--nl` | `--video-record=<0\|1\|-1>`、`--wait-stable/--no-wait-stable` |
| `framework/config.py` | `JEV_NL_THRESHOLD` / `MAX_STEPS` / `TIMEOUT_S` | `JEV_NL_VIDEO_RECORD`、`JEV_NL_WAIT_STABLE` |
| `config.json` | `base_url` / 账号 / `mcp` | `video_record`、`wait_stable` |

> 读取顺序要注意一个坑：**pytest 参数只在 `pytest_generate_tests` / `pytest_configure` 之后才可用**，
> 而 `framework/config.py` 是在 **import 期**读环境变量的（模块级常量）。
> 所以"pytest 传值"不能在 `config.py` 里解析——必须在 runner 收到用例时**按用例解析一次**
> （`resolve_threshold()` 就是同一个套路：`assertions.py` 里按用例覆盖默认阈值）。
> **照抄 `resolve_threshold` 的形态即可**，别把优先级塞进模块级常量。

### 7.2 录屏三档的实现形态（按"最简单"落地）

| 模式 | 录制 | 合成 | 附加到报告 | 说明 |
|---|---|---|---|---|
| `0` 不记录 | **不启动** | — | — | 见下 |
| `1` 记录全部（默认） | 启动 | 编码 | 附加 | 全留 |
| `-1` 仅保留失败 | 启动 | **仅失败时编码** | **仅失败时附加** | 成功的用例连编码都省了 |

**两点实现要点**：

1. **`0` 应当"不启动录制"，而不是"录了再删"。** 录屏本身有开销（实测观察阶段 +3–6 ms/次，
   采集线程持续轮询 + 每帧 ack），"不记录"却照样录一遍再删，等于白付这份开销。
   `-1` 与 `1` 的差别才是"跑完按结果决定"。
2. **"删除"的最佳落点是在 `attach` 之前，而不是之后。** Allure 在 `attach()` 时会把字节
   **拷贝**进 `allure-results/<uid>-attachment.mp4`；一旦附加过，删原文件也删不掉报告里那份。
   所以 `-1` + 通过 的正确形态是：**不编码、不附加**——结果与"生成再删"完全等价，还省掉 **7 秒**编码（实测值）。

**一个必须记住的体积事实**：原始 jpeg 帧约 **92 MB/分钟**（实测），mp4 只有 **约 7 MB/分钟**。
所以**帧目录必须及时清理**，不能只留不管——30 秒的用例会先落 ~46 MB 的帧。

**判定点**：成败要等 `run_case` 的「终局判定」之后才知道，而录制在那之前就开始了。
这正是"一律先录"的原因——**录制无法预判结果，只有清理可以事后决定**。

## 8. 附加分析：把「页面稳定等待」做成报告步骤 + 双开关

> 这一节对应决策 4：**"可以加上等待，并且再分析一下针对这个等待加入报告的执行步骤，
> 能否实现通过环境变量和 pytest 参数实现开关，也是默认开启，批量执行的时候可以通过 pytest 传值关闭。"**

### 8.1 现在的等待散在哪五处

等待**全部发生在库内部**（`browser.py`），runner 现在看不到、也包不进步骤：

| 位置 | 等待 | 量级 |
|---|---|---|
| `browser.py:46` | 首屏 `wait_until_stable(timeout=25, interval=0.6)` | **最大**，E9 上 2–3 s |
| `browser.py:42` | `_settle()`：轮询 `document.readyState == complete`（上限 15 s） | 中 |
| `browser.py:102-104` | 跟随新标签页后的 `_settle()` + `wait_until_stable()` | 中 |
| `browser.py:193-227` | 输入后的控件同步等待：combobox 200 ms / 富文本 500 ms / 其余 50 ms | 小但每步都有 |
| `browser.py:253` | `kind == "wait"` 动作的 `time.sleep(0.1)` | 可忽略 |

`wait_until_stable()` 的算法（`browser.py:107-134`）：反复观察，直到**连续 3 次动作空间签名相同**
（`(len(actions), marker)`）才认为稳定，否则等到超时。

### 8.2 能否做成报告步骤 → **能，但有一个必须解决的前提**

**前提问题**：Allure 的步骤时间戳是 `__enter__`/`__exit__` 时由 `now()` **自动取的**。
如果等待发生在库里（runner 无法把它包进 `with` 块），那这个步骤就会和现在的「执行」步骤一样
**零宽度**——报告里永远显示 0 ms，等于白加。

**这个前提本次已实测解决**（探针 6）：**步骤的 `start`/`stop` 可以事后改成真实区间**。

```python
ctx = allure.step("第 1 步 · 等待页面稳定")
ctx.params = {"稳态样本数": 3}
with ctx:
    real_start = now_ms();  ...库里的等待...;  real_stop = now_ms()
    step = reporter.get_item(ctx.uuid)          # 与 §2.3 路 4 同一个把手
    step.start, step.stop = real_start, real_stop
    step.parameters.append(Parameter(name="等待耗时ms", value=real_stop - real_start))
```

实测落盘：

```text
时长=   351 ms  start=1790220262686  stop=1790220263037
  参数: [{"name": "稳态样本数", "value": 3}, {"name": "等待耗时ms", "value": 351}]
对照（不干预的步骤）: 时长 = 201 ms   ← 就是 with 块的真实时长
```

**所以「等待」步骤能拿到真实区间**，不会重蹈「执行」步骤零宽度的覆辙。

**推荐的设计（设计 A）**：库侧只**记录观测值**，不碰 Allure

```python
# browser.py —— 与 Allure 完全无关，只是把"等了多久、等到了没"记下来
self.last_wait = {
    "kind": "stable",            # stable / settle / input_sync / explicit
    "started_ms": ..., "elapsed_ms": ...,
    "stable": True,              # 是否在超时前等到稳定
    "polls": 7, "timeout": 25,
}
```
runner 读这个字段渲染步骤。**这符合 AGENTS.md 的边界**：库本体不打 `allure.step`，
只是 state 里多一个字段（和 `history` 里多几个字段是同一类改动）。

**不推荐的替代（设计 B）**：让 runner 显式调用等待（把等待从库里挪出来）。
理由是**挪不动**——首屏等待在 `Browser.__init__` 里，runner 拿到 `Agent` 时它已经跑完了。
硬挪会改变库的初始化语义。

### 8.3 能否用环境变量 + pytest 参数开关 → **能，是现成模式**

落点见 §7.1，三级优先级（pytest > 环境变量 > config.json）。库侧需要一个开关入口：

```python
# 库 API 面的扩张：默认值保持现有行为，不改变任何语义
Browser.__init__(self, url, cookies=None, *, wait_stable=True)
Agent.__init__(self, url, goals, *, cookies=None, record_dir=None, screenshots=False, wait_stable=True)
```

> 这是**库公开 API 的扩张**，虽然默认值让现有行为不变，但要在评审时明确
> ——AGENTS.md 要求"框架需求不改变库的语义"，加一个默认 True 的开关不改变语义，
> 但它是库表面的一部分，不是框架内部的事。

### 8.4 ⚠️ 这个开关省不了钱，可能反而更贵（必须先说清楚）

**关掉等待不是免费的。** `wait_until_stable` 存在的全部理由，就是避免
"在渲染中途做决策 → 决策立刻被 `StalePage` 判过期 → 重新观察 → 重新决策"这个循环。
而每一轮重决策都是**一次付费的 TypeSafe 请求**。

所以：

- **关掉等待 → 决策过期率上升 → 模型调用次数上升 → 批量执行可能更贵**，而不是更便宜；
- 它节省的只有 `wait_until_stable` 那几次 `observe()` 的**免费**时间；
- **如果目标真是省钱，更该调小 `timeout`（比如 25 s → 8 s），而不是关掉**——超时后一样会继续往下走，
  但保留了"页面稳定就立刻返回"的快路径。

**因此这个开关的定位应当是"调试/诊断"，而不是"回归省钱"。**
实施时**必须先做一组 A/B 实测**（同一用例开/关各跑一次，比决策请求数与耗时），
拿数据再决定要不要在批量执行里关掉它。**在拿到这组数据之前，建议保持默认开启。**

### 8.5 门槛：只把 ≥200 ms 的等待独立成步骤（**已确认为决策**）

如果每个等待都独立成步骤，一轮循环会从 2 个步骤变成 3 个，报告里会塞满
50 ms 的输入同步等待，反而看不清重点。**已确认的门槛是 200 ms**：

- **耗时 ≥ 200 ms** 的等待 → 独立成「第 N 步 · 等待页面稳定」步骤，带真实区间与参数；
- **< 200 ms** 的短等待 → 不建步骤，把耗时并入它所在步骤的参数（如「执行」步骤的 `输入后同步等待ms`）。

这样"为什么这一步慢"一眼能看到，又不至于把报告变成流水账。
**门槛本身可配置**（`wait_step_threshold_ms`，四级优先级与另外两个开关一致）。

> 依据说明：200 ms 这个数是按**演示站点**的等待分布定的
> （短等待是 50/200/500 ms 三档，首屏稳定等待是秒级）。
> **E9 上的实际分布没测过**，实施期要复核一次是否合适
> （分析报告 §7 待实测第 3 项 → 现见 [实施方案 §13](./二期测试报告优化实施方案.md)）。

> ### ⚠️ 一处归属修正（2026-09-24 写实施方案时复核发现）
>
> **"等待步骤放在决策与执行之间"是错的**——会把等待归属到错误的轮次上。
> 原因：`browser.py` 里的等待，除了首屏那一次，**其余全部发生在 `act` 内部**
> （`follow_new_tab` 的新标签页稳定等待、`observe()` 的输入后同步等待）。
> 放在执行之前，显示的是**上一轮 act** 里发生的等待——**错位一轮，而报告上看不出任何异常**
> （时间区间是真的，只是归属错了）。
>
> **修正**：等待步骤紧跟在**产生它的执行步骤之后**，共用同一个步数编号；
> 且一次 `act` 可能有**多个**等待（新标签页稳定 + 输入后同步），库侧要记**一列表**而不是一个值。
> 完整设计见[实施方案 §7](./二期测试报告优化实施方案.md)。
> **本节以下内容（门槛、开关代价）仍然成立。**

### 9.1 放哪：跟框架一起，纳入 Git

3. **README 里写清升级清单**：升级 Allure CLI / allure-pytest 时，
   按顺序跑「版本校验 → 生成报告 → 看插件是否渲染 → 跑 eval」。
   最该先跑的就是那条 eval。
