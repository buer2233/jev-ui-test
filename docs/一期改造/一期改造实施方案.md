## 3. 关键设计一：两级断言（对应要求 1）

### 3.1 为什么必须是两级

你的要求里其实包含一个很重要的区分，值得先讲清楚：

- **执行期**：模型要**连续做几十次判断**（下一步点哪里、填什么）。这里用 Jev 概率是对的——需要泛化、需要打分、需要从候选中排序。**现状已经如此，不动。**
- **终局**：只需**一次是非判断**。如果这里也用"问模型通过了吗"，就掉进了 `AGENTS.md` 明确禁止的陷阱：**「A DONE choice is not proof of success」**——被测对象和判分者是同一个模型的同一次判断，错了会一起错。

所以终局必须是 **pytest 的 `assert`**：它是**确定性**的（同一个输入必然同一个结果）、**可复现**的、**失败时有明确堆栈**的。AI 只负责提供"语义识别"这一项人类难以用代码表达的能力，**判定权始终在代码手里**。

### 3.2 断言 DSL（写在 YAML 的 `expect` 里）

| `type` | 用途 | 确定性? | 参数 |
|---|---|---|---|
| `ai` | **语义断言**：自然语言描述页面状态 | 概率 + 代码阈值 | `claim`、`threshold`(缺省取全局配置，见 §3.5) |
| `url_contains` | URL 包含某子串 | ✅ 完全确定 | `value` |
| `url_equals` | URL 相等（可忽略 query/hash） | ✅ | `value`、`ignore_query` |
| `text_contains` | 页面可见文本包含 | ✅ | `value`、`count`(可选，出现次数) |
| `text_not_contains` | 页面可见文本不包含 | ✅ | `value` |
| `element_exists` | 存在 label 匹配的可操作元素 | ✅ | `label`、`role`(可选)、`exact`(默认 False) |
| `element_absent` | 不存在匹配元素 | ✅ | `label` |
| `element_value` | 元素的当前值 | ✅ | `label`、`equals` 或 `contains` |
| `element_count` | 匹配元素的数量（**"某某数据应该显示多少"的确定性版本**） | ✅ | `label_contains`、`equals` / `min` / `max` |
| `element_enabled` | 元素未被禁用 | ✅ | `label` |

### 3.3 "某某数据应该显示多少" 的两种写法

这是你特别点到的场景，给两种：

```yaml
# 写法 A（AI 识别，适合数字嵌在自然语言文案里）
- type: ai
  desc: 结果计数文案显示 3 条
  claim: 页面上显示的结果条数为 3 条
  threshold: 0.6

# 写法 B（确定性计数，适合数字是列表条目数）
- type: element_count
  desc: 结果列表应有 3 条
  label_contains: "View stay"
  equals: 3
```

**建议**：能用 `element_count` 就用 B（零成本、零抖动）；只有数字嵌在句子/图片/复杂渲染里时才用 A。

### 3.4 实现骨架

```python
# jev_ultrafast/framework/assertions.py
"""终局断言层：把 YAML 的 expect 变成 pytest 能 assert 的确定性结果。

设计要点：
- 每个 checker 只回答「这条预期是否成立」+「证据是什么」，不自己抛断言。
- 是否通过由调用方（runner）用 assert 决定，保证失败能被 pytest 正常捕获与报告。
"""

def check(page, expect, *, judge_ctx) -> dict:
    """返回 {"ok": bool, "detail": str, "evidence": dict}。"""
    kind = expect["type"]
    checker = CHECKERS.get(kind)
    if checker is None:
        raise ValueError(f"未知的断言类型 {kind!r}；可用：{sorted(CHECKERS)}")
    return checker(page, expect, judge_ctx)


def check_ai(page, expect, judge_ctx):
    """语义断言：交给 Jev 的 noul 做真值判断，阈值比较留在代码里。

    为什么用 noul 而不是让模型直接回答"通过/不通过"：
    noul 返回的是【页面状态是否满足该陈述】的连续概率，
    是一个关于页面的事实判断，与"我刚才做得对不对"无关，
    因此不会与被测行为产生自证循环。判定阈值由代码持有。
    """
    # 阈值三级优先级：断言级 > 用例级 > 全局默认（见 §3.5）
    threshold = float(expect.get("threshold", judge_ctx.default_threshold))
    result = judge_ctx.judge([expect["claim"]])[0]      # 一次请求可批量问多条
    probability = result["noul"]
    ok = probability >= threshold                        # ← 确定性比较，代码持有
    return {
        "ok": ok,
        "detail": (
            f"语义断言{'通过' if ok else '未通过'}：{expect['claim']}；"
            f"noul={probability:.3f}，阈值={threshold}"
        ),
        "evidence": {"claim": expect["claim"], "noul": probability, "threshold": threshold},
    }
```

runner 里：

```python
for expect in case["expect"]:
    with allure.step(f"断言：{expect.get('desc') or expect.get('claim') or expect['type']}"):
        result = check(page, expect, judge_ctx=ctx)
        allure.attach(
            json.dumps(result["evidence"], ensure_ascii=False, indent=2),
            "断言证据", allure.attachment_type.JSON,
        )
        # 关键：assert 在 allure.step 内，失败会同时进报告和 pytest 结果
        assert result["ok"], result["detail"]
```

`★ Insight ─────────────────────────────────────`
这个设计的关键不在代码，而在**职责边界**：AI 只产出"证据"（一个 0–1 的概率），代码持有"判定"（阈值比较 + assert）。
于是：
- 失败时你能在 Allure 里看到 `noul=0.42, 阈值=0.6` —— 是"模型认为没做到"还是"确实没做到"，一眼可辨；
- 想调松紧只改一个数字，不用改 prompt；
- 断言永远可复现（同一页面文本 → 同一概率，模型侧非确定性被隔离在这一层之外）。
`─────────────────────────────────────────────────`

### 3.5 阈值：默认 0.75，三级可调

实测：真值 **0.97**、假值 **0.01**（中文断言）；但**语义模糊的断言会落到 0.53**（分析报告 §3.7）。0.75 落在 0.53 与 0.97 之间，比 0.6 更严格，同时仍留有余量。

**默认值收在一个常量里，用例可以覆盖，环境变量可以整体调。**

```python
# jev_ultrafast/framework/config.py  ← 全框架唯一的阈值默认值落点
"""框架级可调配置。所有默认值集中在此，避免散落在各处。"""

# 语义断言（ai 类型）的默认通过阈值。
# 依据：实测真值 0.97、假值 0.01，模糊断言会落到 0.53。
# 调松会放过半对的结果，调紧会让模糊但成立的断言失败——改前请先看 Allure 里的概率分布。
DEFAULT_AI_THRESHOLD = float(os.environ.get("JEV_NL_THRESHOLD", "0.75"))

# 单用例最大浏览器动作数与最大决策请求数（内层循环预算）
DEFAULT_MAX_STEPS = 60
DEFAULT_MAX_DECISIONS = 120

# 单用例整体超时（秒）
DEFAULT_TIMEOUT_S = 240
```

**三级优先级**（就近覆盖，从高到低）：

| 级别 | 写在哪 | 用途 |
|---|---|---|
| ① 断言级 | `expect[].threshold` | 个别断言需要更松/更紧 |
| ② 用例级 | `cases[].threshold` 或 `defaults.threshold` | 整个用例的阈值口径统一 |
| ③ 全局 | `framework/config.py: DEFAULT_AI_THRESHOLD`，可用环境变量 `JEV_NL_THRESHOLD` 覆盖 | 日常调参只改这一处 |

```python
def resolve_threshold(expect, case, framework_default):
    """三级优先级解析：断言级 > 用例级 > 全局默认。"""
    for value in (expect.get("threshold"), case.get("threshold"), framework_default):
        if value is not None:
            return float(value)
    return float(framework_default)
```

**配套要求**

- **每条断言的原始概率都写进 Allure**——调阈值前先看真实分布，不要凭感觉调；
- 断言写得**原子**（一句话只判一件事）——这是拉开 0.97 与 0.53 差距的关键，比调阈值更有效；
- CI 上可用 `JEV_NL_THRESHOLD` 临时放宽做冒烟，但**默认必须保持 0.75**。

### 3.6 多断言如何合成：逐用例决定（不设全局默认口径）

你指出的问题是对的：**"全部满足"和"满足其一"是业务语义，不是框架偏好**，必须由每条用例自己声明。所以合成规则写在 YAML 用例级：

```yaml
    expect_mode: and        # and（默认）| or | min_pass
    min_pass: 2             # expect_mode: min_pass 时生效
    expect:
      - type: ai
        claim: 页面上显示了 Casa Flora 的详情介绍
      - type: url_contains
        value: "#casa-flora"
      - type: text_contains
        value: "Destination Lisbon"
```

| `expect_mode` | 语义 | 典型场景 |
|---|---|---|
| `and`（默认） | 全部通过才通过 | "搜索成功 **且** 筛选生效 **且** 打开了详情页"——完整业务流程 |
| `or` | 任一条通过即通过 | "能通过菜单进入 **或** 通过搜索进入"——多种等效路径 |
| `min_pass` | 至少 N 条通过 | "4 项筛选里至少 3 项生效"——允许部分缺失的宽松校验 |

实现要点：

```python
# jev_ultrafast/framework/assertions.py

def combine(results, mode="and", min_pass=None):
    """把多条断言结果合成为一个终局判定。

    注意：这里只做合成，不抛异常；最终的 assert 由 runner 执行，
    以便失败信息里能带上全部断言的明细（而不只是第一条失败的）。
    """
    passed = [r["ok"] for r in results]
    if mode == "and":
        ok = all(passed)
        detail = f"{sum(passed)}/{len(passed)} 条断言通过（要求全部通过）"
    elif mode == "or":
        ok = any(passed)
        detail = f"{sum(passed)}/{len(passed)} 条断言通过（要求任一通过）"
    elif mode == "min_pass":
        need = int(min_pass or 1)
        ok = sum(passed) >= need
        detail = f"{sum(passed)}/{len(passed)} 条断言通过（要求至少 {need} 条）"
    else:
        raise ValueError(f"未知的 expect_mode={mode!r}；可用 and / or / min_pass")
    return {"ok": ok, "detail": detail, "results": results}
```

runner 里：

```python
results = []
for expect in case["expect"]:
    with allure.step(f"断言：{expect.get('desc') or expect.get('claim') or expect['type']}"):
        result = check(page, expect, judge_ctx=ctx)
        results.append(result)
        allure.attach(json.dumps(result["evidence"], ensure_ascii=False, indent=2),
                      "断言证据", allure.attachment_type.JSON)

verdict = combine(results, case.get("expect_mode", "and"), case.get("min_pass"))
with allure.step("终局判定"):
    # 全量明细附上，失败时能一眼看出是哪几条没过、各自概率多少
    allure.attach(json.dumps(verdict, ensure_ascii=False, indent=2),
                  "断言汇总", allure.attachment_type.JSON)
    assert verdict["ok"], verdict["detail"] + "；明细见「断言汇总」附件"
```

`★ Insight ─────────────────────────────────────`
**为什么合成放 `and`/`or`/`min_pass` 三种，而不是只做 and/or？**

纯 `or` 有个陷阱：**它会让"根本没做事"也通过**。比如 3 条断言里有一条是"页面没有报错提示"——如果这条恰好成立，`or` 就直接判过了，即使业务流程完全没走通。

`min_pass: N`（N ≥ 2）能表达"允许多条等效路径，但要求多数成立"，比 `or` 更贴合"多种等效入口"这类真实场景。建议：**能用 `and` 就用 `and`；确实有多路径时才用 `or`，且优先考虑 `min_pass`。**

另外注意：`or` 与 `min_pass` 都**弱化**了断言强度。`api-test-E9/AGENTS.md` 明确禁止"通过弱化断言获得 GREEN"，所以建议在评审时对 `expect_mode: or` 的用例额外过一眼。

## 4. 关键设计二：YAML 用例组织（对应要求 5）

### 4.1 为什么是 YAML（对比另外两种）

| 方案 | 优点 | 缺点 | 结论 |

### 4.5 pytest 收集机制

```python
# tests/conftest.py
import pytest
from jev_ultrafast.framework.loader import load_cases

def pytest_generate_tests(metafunc):
    """把 cases/*.yaml 收集成参数化用例。

    为什么用 pytest_generate_tests 而不是 @pytest.mark.parametrize：
    用例是运行时从 YAML 读的，数量与内容都不在代码里，
    参数化装饰器需要静态列表，做不到。
    ids 用 case["id"]，保证 Allure 历史趋势与 -k 选择都稳定。
    """
    if "nl_case" not in metafunc.fixturenames:
        return
    cases = load_cases(metafunc.config)          # 支持 -k / --case-dir 过滤
    metafunc.parametrize("nl_case", cases, ids=[c["id"] for c in cases])
```

```python
# tests/test_nl_cases.py
import allure, pytest

@pytest.mark.nl_case
def test_natural_language_case(nl_case, run_case):
    """一个 YAML 用例 → 一个 pytest 用例 → 一个 Allure story。"""
    # 用例标题包上 @allure.story（要求 3）
    allure.dynamic.story(nl_case["name"])
    allure.dynamic.feature(nl_case.get("feature", "未分类"))
    allure.dynamic.epic(nl_case.get("epic", "E9-UI自动化"))
    allure.dynamic.title(nl_case["name"])
    allure.dynamic.description(nl_case["goal"])
    if nl_case.get("severity"):
        allure.dynamic.severity(nl_case["severity"])
    run_case(nl_case)
```

`★ Insight ─────────────────────────────────────`
**为什么 `@allure.story` 要用 `allure.dynamic` 而不是装饰器？**

`@allure.story("标题")` 是**装饰器**，参数在**导入时**就必须是常量。而这里的用例标题来自运行时读到的 YAML——导入 `test_nl_cases.py` 时根本还不知道有哪些用例。

`allure.dynamic.*` 是等价的运行时 API，作用完全相同，只是求值时机从"导入期"挪到了"执行期"。这是"数据驱动 + Allure"的标准解法。

同理，你要求"每条用例的标题包上 `@allure.story`"——在数据驱动下就是**每个 YAML 用例的 `name` 自动成为一个 story**，比手写装饰器更不容易漏。

## 5. 关键设计三：Allure 接入（对应要求 3）

### 5.1 层级映射

```
epic        E9-UI自动化                     ← YAML epic
└ feature   门户 / 流程 / 本文档             ← YAML feature
  └ story   搜索里斯本住宿并打开 Casa Flora   ← YAML name（要求 3）
    └ 用例   test_natural_language_case[stay-search-lisbon]
      ├ step 前置：接口登录并注入浏览器登录态
      ├ step 第 1 步 · 决策（Jev 概率判断）
      ├ step 第 1 步 · 执行 TYPE_TEXT → Destination
      ├ step 第 2 步 · 决策（Jev 概率判断）
      ├ ...
      └ step 断言：已打开 Casa Flora 详情页
```

### 5.2 步骤包装放在哪（**不要**装饰 `agent.py`）

你要求"给执行操作方法包上 `allure.step`"。**建议包在框架层的 `runner.py`，而不是 `agent.py` 上打装饰器。**

理由：

1. `agent.py` 是**库**，`demo.py`（inspector）也依赖它。给它打 `allure.step` 会让一个本地演示工具莫名依赖 `allure-pytest`，并污染 `snapshot()` 的返回结构。
2. 步骤标题需要**动态内容**（第几步、什么操作、什么目标），装饰器做不到，只能用 `with allure.step(...)` 上下文管理器。
3. 项目约定「`agent.py` 是完整可读的循环」——保持它干净。

```python
# jev_ultrafast/framework/runner.py
import allure

class TracedRun:
    """把 Agent 的每一轮循环包成 Allure 步骤，并留痕决策概率与截图。"""

    def __init__(self, agent, case):
        self.agent = agent
        self.case = case
        self.step = 0

    def run(self):
        with allure.step("前置：接口登录并注入浏览器登录态"):
            ...  # 见 §6

        while self.agent.state["status"] not in {"done", "blocked"}:
            self.step += 1

            with allure.step(f"第 {self.step} 步 · 决策（Jev 概率判断）"):
                snapshot = self.agent.command("predict")
                decision = self.agent.state["decision"]
                # 决策概率作为 step 参数，报告里可直接看到模型"有多确定"
                allure.attach(
                    json.dumps(decision, ensure_ascii=False, indent=2),
                    "Jev 决策概率", allure.attachment_type.JSON,
                )

            if self.agent.state["status"] in {"done", "blocked"}:
                break

            with allure.step(f"第 {self.step} 步 · 执行 {decision['operation']} → {decision['choice']}"):
                self.agent.command("act", {"fingerprint": self.agent.state["page"]["fingerprint"]})
                if self.case.get("on_failure", {}).get("screenshot", True):
                    self._attach_screenshot()

        with allure.step("终局：加载最终页面状态"):
            ...
```

```python
移植自 api-test-E9 的 page_api/login_api/login_api.py（同一位作者），

"""

RSA_PATH = "/rsa/weaver.rsa.GetRsaInfo"
LOGIN_PATH = "/api/hrm/login/checkLogin"
REMIND_PATH = "/api/hrm/login/remindLogin"

def _browser_headers(base_url, *, form=False, origin=False):
    """按 HAR 约定构造 Ajax 请求头；E9 所有 Ajax 接口共用此模板。"""
    ...

def login(base_url, user_name, password, *, timeout=30):
    """接口登录并返回可直接交给 CDP 的 cookie 列表。

    Returns:
        list[dict]: [{"name":..., "value":..., "url":..., "path":...}, ...]
                    形如 CDP Network.setCookie 的参数，调用方无需再转换。
    Raises:
        RuntimeError: 登录业务码或登录态异常时抛出，且消息中不含凭据。
    """
    session = requests.Session()
    session.headers["User-Agent"] = BROWSER_UA
    base = base_url.rstrip("/")

    # 1) RSA 配置（E9 登录页前置）
    rsa = session.get(base + RSA_PATH, params={"ts": _timestamp()}, headers=_browser_headers(base), timeout=timeout)
    rsa.raise_for_status()

    # 2) 提交登录表单
    login = session.post(base + LOGIN_PATH, data={...}, headers=_browser_headers(base, form=True, origin=True), timeout=timeout)
    login.raise_for_status()
    data = login.json()
    if data.get("msgcode") != "0" or data.get("loginstatus") != "true":
        # 只报非敏感诊断字段，避免凭据/token 进日志
        raise RuntimeError(f"E9 登录失败：msgcode={data.get('msgcode')} loginstatus={data.get('loginstatus')}")

    # 3) 登录提醒（E9 抓包链路的一环，缺失可能影响后续会话）
    session.post(base + REMIND_PATH, data={"logintype": "1", "appid": "", "service": ""},
                 headers=_browser_headers(base, form=True, origin=True), timeout=timeout)

    return [
        {"name": c.name, "value": c.value, "url": base, "path": c.path or "/"}
        for c in session.cookies
    ]
```

### 6.3 Cookie 注入浏览器的实现

### 6.5 ⚠️ 一期最关键的技术缺口：E9 的交互元素 `snapshot.js` 看不见

**这是本次复验最重要的发现，直接决定一期要额外做多少工作。**

免登录进入工作台后，实测动作空间的对比：

| 指标 | 实测值 |
|---|---|

|---|---|---|---|
| `DIV` | `e9header-home` | 我的门户 | ❌ |

| `DIV` | `e9header-freq-use-menu` | 常用菜单 | ❌ |
| `DIV` | `e9header-remind-icon` | 消息中心 | ❌ |
| `DIV` | `e9header-toolbar-item-icon` | 收藏夹 | ❌ |
| `DIV` | `e9header-toolbar-more-icon` | 更多 | ❌ |
| `DIV` | `ant-menu-submenu-title` | （Ant Design 菜单） | ❌ |

**结论修正**：早前曾怀疑这是 **iframe** 问题，**已排除**。实测 `#mainFrame` 恒为 `about:blank`（观察 57 秒不变），不是内容载体；工作台内容就在顶层文档里，只是标记方式不被现有选择器识别。E9 前端使用 **Ant Design Vue**（`ant-*` class）。

## 7. 关键设计五：文本模型思考参数（对应要求 4）

### 7.1 实测数据（同一 prompt，`max_tokens=1024`）

| 参数写法 | 推理 token | 耗时 | 结论 |
|---|---|---|---|
| `reasoning: {enabled: false}` ← **当前行为** | 31/39 | 2771 ms | ❌ 端点**不认**，思考没关掉 |
| 不发任何 reasoning 字段 | 23/31 | 6044 ms | ❌ 更慢 |
| `reasoning: {effort: low}` | 23/31 | 2941 ms | ❌ 仍未关掉 |
| **`enable_thinking: false`** | **0/7** | **1837 ms** | ✅ **阿里云百炼正确写法** |
| **`thinking: {type: disabled}`** | **0/7** | **2061 ms** | ✅ DeepSeek 官方写法 |

**当前配置 `TEXT_MODEL_REASONING=none` 发出的 `{"reasoning": {"enabled": false}}` 被端点忽略**，白白多花约 900 ms，还引入一个真实故障模式：`max_tokens` 被推理吃光后 `content` 返回**空串**，业务表现为"字段填不进去"（本次用 `max_tokens=256` 时实际复现了）。

### 7.2 改法：按端点分派

```python
# jev_ultrafast/model.py —— 替换 field_text 内的 reasoning 计算（约 10 行）

def _reasoning_fields(base):
    """按端点选择真正能关掉思考的参数形态。

    不同网关认不同的字段名，发错了不会报错，只会静默继续思考：
      阿里云百炼/DashScope 兼容模式  → enable_thinking
      DeepSeek 官方                  → thinking.type
      OpenRouter / 通用              → reasoning.enabled
    实测数据见 docs/一期改造/一期改造可行性分析报告.md §3.4。
    """
    override = os.environ.get("TEXT_MODEL_REASONING", "none")
    if override not in ("none", ""):
        # 显式覆盖：允许诊断时切换成 low/medium/high
        return {"reasoning": {"effort": override}}

    if "aliyuncs.com" in base or "dashscope" in base:
        return {"enable_thinking": False}
    if "api.deepseek.com" in base:
        return {"thinking": {"type": "disabled"}}
    return {"reasoning": {"enabled": False}}
```

调用处：

```python
reasoning = _reasoning_fields(base)
```

**保留 `TEXT_MODEL_REASONING` 作为显式覆盖开关**，语义从"none/enabled"改成"none 或 思考档位"，向后兼容现网 `.env`（`none` 仍表示"关掉"，只是关的方式对了）。

**验收**

> **注意（本次实测踩到的坑）**：`browser_harness` 的 IPC 响应超时默认是 **5 秒**（`helpers.py: _send`）。E9 页面 `Page.captureScreenshot` 实测耗时 **3315 ms**，接近临界；页面更重时会超时并抛 `_IPCResponseTimeout`。需要给截图等重调用显式放宽 `_response_timeout`（`cdp()` 支持该参数）。建议统一在 `Browser.call` 上加一个可配置的超时。

3. 给 `questions.py` 补充对应指令语义；
4. 控制候选数量，避免 170 个 div 淹没 250 的上限。

**验收**

- E9 工作台上 `snapshot.js` 能发现 **≥ 15** 个可操作元素（当前是 1）；
- Agent 能用自然语言通过菜单导航到至少一个功能模块；
- **现有 21/21 浏览器守卫检查与 32 个既有单测仍然全绿**（防止回归）。

### M6 · 真实用例试跑与标定

**做什么**

2. 统计卡住的比例与原因分布（元素发现 / 执行 / 断言）；

**验收**：得到"可自动化比例"与"单用例成本"两个数字，作为是否进入二期的依据。

## 10. 风险与待确认

| 风险 | 影响 | 应对 |
|---|---|---|
| **E9 交互元素不被 `snapshot.js` 识别**（§6.5） | **一期最大缺口**：当前动作空间基本为空，无法导航 | 已定位且验证可行（§6.6）；列为 **M5 独立里程碑**，有明确验收判据 |
| ~~E9 环境处于升级故障态~~ | ~~M4 无法验收~~ | ✅ **已修复并复验通过**（§6.1） |
| 扩大选择器后动作空间被噪声淹没 | 决策质量下降、token 成本上升 | 优先 `[ecid]` 逐步放宽；沿用 250 候选上限；每次放宽都跑回归 |
| 断言阈值标定不足 | 偶发误判 | 默认 **0.75**（`framework/config.py` 可调）+ 概率全量留痕；关键断言叠加确定性 checker |
| `expect_mode: or` / `min_pass` 弱化断言 | 掩盖真实缺陷 | 评审时对非 `and` 的用例额外过一眼（`api-test-E9/AGENTS.md` 禁止为 GREEN 弱化断言） |
| 步骤级重试会重复提交 | 业务数据被污染 | **只允许用例级重跑**（`--reruns`），并把这条写进框架契约与文档 |
| 凭据进入公网仓库 | **安全事故** | §6.4 的 `.gitignore` + 提交前 grep 门禁 |
| 重页面的 CDP 调用超过 5 s IPC 超时 | `_IPCResponseTimeout` 中断用例 | M4 里统一放宽截图类调用的 `_response_timeout`（实测截图 3315 ms） |
| 单用例成本随页面变大 | 预算超支 | M6 测基线；`snapshot.js` 已有 6000 字符 / 250 元素上限兜底 |

**已确认（原待确认项）**

1. ✅ **断言阈值**：默认 **0.75**，落在实测"模糊断言 0.53"与"真值 0.97"之间；收在 `framework/config.py: DEFAULT_AI_THRESHOLD`，三级可覆盖（§3.5）。
2. ✅ **多断言合成**：**逐用例声明**，提供 `and` / `or` / `min_pass` 三种（§3.6）。
3. ✅ **E9 入口 URL**：确认为 `/wui/index.html`（§6.1 已验证 200 且进入工作台）。

**仍需你确认的一点**

- **`[ecid]` 选择器是否会在 E9 各模块页面上稳定存在？** 本次只在工作台首页验证了它（13 个元素）。建议在 M5 开始时，先在 3–5 个真实功能模块页面上确认 `[ecid]` 的覆盖率；若覆盖不全，就需要回退到「带 `title` 且无原生子控件的 div」这条次选策略（噪声更大，需要更谨慎的过滤）。
