# 一期改造可行性分析报告

> 目标设想：把 jev-ultrafast 改造为**自然语言驱动的 UI 自动化测试框架**——用例以自然语言编写，由 pytest 执行，用 Allure 展示报告。
>
> 本报告基于对当前项目源码的完整通读，以及在本机真实调用正式 jev 模型与文本大模型跑出的实测数据。所有实测结论都附有原始证据与复现命令。

---

## 0. 结论摘要

**判断：可行。核心链路已在本机端到端跑通，不需要推翻现有架构，属于"增量扩展"而非"重写"。**

一句话理由：jev-ultrafast 已经把最难的部分（**把页面变成有限动作空间、把自然语言目标变成可执行决策、把模型输出挡在可执行代码之外**）做完了；缺的部分集中在**用例承载**和**断言**两处，而断言所需的模型能力（TypeSafe 的 `noul` / `score`）经实测已经具备，只是当前代码没用。

| 能力项 | 现状 | 判断 |
|---|---|---|
| 浏览器驱动（CDP、后台标签页、无头式隔离标签） | 已有，实测 21/21 通过 | ✅ 直接可用 |
| 自然语言目标 → 可执行动作 | 已有（TypeSafe 决策） | ✅ 直接可用 |
| 中文自然语言用例 | **实测支持**（断言判别 0.97 vs 0.01） | ✅ 直接可用 |
| 自然语言断言 / 预期结果校验 | **缺失**（现有断言是手写 Python） | ⚠️ 需新增，但模型侧已就绪 |
| pytest 承载 | 部分（tests/ 只有离线单测） | ⚠️ 需新增用例层 |
| Allure 报告 | 完全没有 | ⚠️ 需新增；**本机有版本坑，已实测出可用组合** |
| 用例级隔离 | 缺失（共享 Chrome 默认上下文） | ⚠️ 需新增；**实测证明一行 CDP 调用即可实现** |
| 并行执行 | 缺失 | ❌ 一期建议不做 |

**最大的未验证风险**：本报告所有端到端实测都在项目的**本地 fixture 页面**上完成。真实目标（E9 workspace UI）若大量使用 iframe / 复杂表格 / canvas / 自定义控件，命中 README 明确列出的能力边界，成功率需另行验证。**这是立项后第一件要做的事。**

> **【2026-09-23 补充：该风险已实测，结论与本报告的初始猜测不同】**
>
> 在真实 E9 环境（`/wui/index.html`，免登录注入后）完成探针后，实测结果是：
> - ❌ **不是 iframe 问题**。`#mainFrame` 恒为 `about:blank`（观察 57 s 不变），不是内容载体。
> - ✅ **是元素发现问题**。E9 的导航/菜单/门户组件用 **`<div>` + class + JS 事件委托**（带自有标识 `[ecid]`），而 `snapshot.js` 的选择器只认原生控件与 ARIA role——**实测页面有 19 个 E9 风格交互元素，`snapshot.js` 只发现 1 个**。当前状态下 Agent 连菜单都点不开。
> - ✅ **执行路径无问题**。用 jev 现有的 CDP 鼠标事件路径点击这类 div，**3/3 产生真实 DOM 变化**（含不点击对照组排除自抖动）。
> - ✅ E9 全屏防截屏水印 `pointer-events: none`，不干扰点击命中判定。
>
> 因此本文 §4.3 与 §5.5 中"优先补 `snapshot.js` 的 frame 遍历"的说法**应予修正**为"优先扩展 `snapshot.js` 的元素发现范围（`[ecid]` 等）"。详见 [一期改造实施方案.md](./一期改造实施方案.md) §6.5–6.7。

## 1. 现状剖析：jev-ultrafast 到底是怎么实现的

### 1.1 一句话架构

```
                一句自然语言目标
                       │
   ┌───────────────────▼────────────────────┐
   │  snapshot.js  ：把当前页面压成          │
   │  「索引化元素表 + 可见文本 + 指纹」      │
   └───────────────────┬────────────────────┘
                       │  elements / targets / controls
   ┌───────────────────▼────────────────────┐
   │  TypeSafe(Jev) ：一次请求同时回答       │
   │  「做哪个操作」+「对哪个元素」           │
   │  只能从已观测元素里选，不能生成选择器     │
   └───────────────────┬────────────────────┘
                       │  operation + target
          ┌────────────┴────────────┐
          │                         │
    TYPE_TEXT                   其它操作
          │                         │
   文本大模型生成字段值              │
          └────────────┬────────────┘
                       ▼
              Browser.act() 执行（CDP）
                       │
                 重新观察 → 循环
```

### 1.2 源码地图（全项目仅 1841 行，可完整通读）

| 文件 | 行数 | 职责 |
|---|---|---|
| `jev_ultrafast/agent.py` | 174 | **主循环**：predict → act → observe，状态机与预算控制 |
| `jev_ultrafast/browser.py` | 194 | CDP 连接、原子观察、新鲜度校验、动作执行 |
| `jev_ultrafast/model.py` | 198 | TypeSafe 决策请求构造 + 文本辅助模型 |
| `jev_ultrafast/questions.py` | 26 | 给模型的指令文本（NEXT_ACTION / TARGET / TEXT_VALUE）+ `MAX_STEPS=60` |
| `jev_ultrafast/snapshot.js` | 107 | **在页面内执行**的 DOM 快照器，产出动作空间 |
| `jev_ultrafast/demo.py` | 145 | 本地 inspector（回环 HTTP 服务，非测试框架所需） |

### 1.3 主循环详解

`Agent.command()` 是唯一的入口，接受三个命令（`agent.py:52`）：

- **`predict`**：调用 `model.choose(page, goal, history)` → 得到一个"选择"。同时把决策连同当时页面的 `fingerprint` 一起存入 `state["decisions"]`。
- **`act`**：执行决策。**执行前先比对 fingerprint**，不一致就抛 `StalePage` 丢弃决策重新观察（`agent.py:88`）。
- **`tick`**：predict + act 的组合，`Agent.run()` 就是循环 tick 直到状态变成 `done` / `blocked`（`agent.py:163`）。

三个安全设计值得注意，它们直接决定了框架能不能被信任：

1. **决策一次性消费**（`agent.py:91`）：执行前就把 `state["decision"]` 置空，"重试不会变成双击"。
2. **先记录执行、再观察结果**（`agent.py:120-142`）：即使动作后的观察遇到页面跳转失败，已执行的动作也不会从历史里消失。
3. **模型输出永不变成可执行物**：TypeSafe 返回的目标必须是**已观测元素的索引**，执行时再由代码从 `window.__jevFast.nodes` 里取出真实 DOM 节点（`browser.py:144-160`），并重新做可见性、禁用态、几何位置、遮挡（`elementFromPoint`）检查。模型无法产生选择器、坐标、JS 或 shell 命令。

`★ Insight ─────────────────────────────────────`
第 3 点是这个项目最值钱的部分，也是它适合做测试框架的根本原因：**它把"LLM 幻觉"的爆炸半径限制在"选错元素"**，而不是"执行任意代码"。对企业内网系统的自动化测试，这个性质比速度重要得多。
`─────────────────────────────────────────────────`

### 1.4 动作空间：`snapshot.js` 是真正的核心

每次观察都执行一次 `READ_STATE`（一个立即执行的 JS 函数），原子地产出：

- **`actions[]`**：索引化的可操作元素。每个元素带 `id`(如 `e1`)、`kind`、`role`、`label`、`value`、`rect`，下拉框还会按选项展开成多条（`kind: select`，`label` 形如 `Stay category → Design`）。
- **`text`**：可见文本，截断到 6000 字符（`snapshot.js:84-92`）。
- **`marker` / `page_key` / `guards`**：三种粒度的指纹，用于判"页面是否已变"。

操作类型由 DOM 反推，**不支持的一律不出现**：

| kind | 触发条件 | 映射到 |
|---|---|---|
| `click` | 可点元素（含只读输入框的"打开"动作） | `CLICK` |
| `fill` | 可编辑的 textbox/searchbox/spinbutton/combobox | `TYPE_TEXT` |
| `select` | 原生 `<select>` 的**每个未选中选项** | `SELECT` |
| `scroll` / `wait` | 视情况追加 | `SCROLL_*` / `WAIT` |
| — | 始终追加为决策项 | `DONE` / `BLOCKED` |

**关键细节**：`snapshot.js:9` 的 `safe()` 过滤掉 `password` / `file` / `hidden`——密码值永远不会进入模型上下文。`snapshot.js:99-100` 限制最多保留 250 个候选动作，被截断的候选无法被选中。

### 1.5 模型层：两个模型的职责边界

**决策模型（TypeSafe / Jev）**——`model.choose()`：

一次 HTTP 请求 `POST https://api.typesafe.ai/v1/systemone`，body 结构：

```json
{
  "model": "<TYPESAFE_MODEL，默认 jev-latest>",
  "state": { "page": {url,title,text}, "elements": [...], "recent_actions": [...] },
  "questions": {
    "operation":        {"type":"choice", "criteria": {CLICK:..., TYPE_TEXT:..., DONE:..., BLOCKED:...}},
    "click_target":     {"type":"choice", "criteria": {"1": {...}, "2": {...}}},
    "type_text_target": {"type":"choice", "criteria": {...}}
  }
}
```

设计要点：**所有 question 在一次请求里并行回答**（speculative fan-out），"选操作"和"选目标"共享同一份观测状态，一次网络往返拿到全部答案。**只有被选中操作对应的那个 target head 会被消费**（`model.py:127`），所以没被选中的 head 即使返回垃圾也不影响执行——`tests/test_agent.py:99` 专门测了这一点。

响应校验非常严格（`model.validate_choice`）：选择必须在候选集内、概率分布必须覆盖全部候选、概率必须归一化到 0.02 以内、被选项必须是最大概率、数值必须有限。任何一条不满足就抛错，**不执行任何动作**。这是防幻觉的关键闸门。

**文本模型**——`model.field_text()`：仅当操作是 `TYPE_TEXT` 时才调用。走 OpenAI 兼容的 `/chat/completions`，要求返回严格的 `{"text": "..."}`（`questions.py:21` 的 `TEXT_VALUE` 指令）。值必须非空、长度 ≤2000、且**对象只能有 `text` 这一个键**，否则视为无效、什么都**不输入**（`model.py:187-193`）。

> 注意：**模型不会去"抠"目标字符串里的引号内容**。`tests/test_agent.py:143` 明确测了 `'Fly from "Zurich" to London'` 仍然走大模型生成，而不是直接提取 `Zurich`。这是刻意的——换取泛化能力。

### 1.6 新鲜度机制：防止"照着过期地图开车"

这是并发/异步页面上最容易出错的地方，项目处理得相当细致：

- **`StalePage` 异常**是一条独立的控制流：决策过期 → 丢弃决策 → 重新观察 → 重新决策，但**已执行的动作不会被撤销或重放**。
- **三档指纹粒度**：
  - 终态判断（DONE/BLOCKED、打字、滚动、等待）用 `marker`——完整语义比对。
  - 点击/选择用 `guards`——只比对**目标元素本身 + 它的邻近上下文**（最近的 form/dialog/li/tr），因此页面上无关区域的变化**不会**让决策失效。
  - `check_guards.py:86-89` 专门验证了这个取舍：`#unrelated` 文本变化后，点击守卫仍认为有效。
- **执行前重取几何**：即使元素移动了，也能点到它的**当前位置**（`check_guards.py:23-27`），不需要额外一次模型调用。
- **失败不重试**：`agent.py:90` 的注释是"Consume once, before any mutation or model call. A retry cannot double-click."，`AGENTS.md` 则明确写成"Never retry a browser mutation"。原生下拉框的变更事件可能已经触发，此时按"过期"处理再重试会导致重复提交，所以 `browser.py:130` 改为抛不可重试的 `RuntimeError`。

### 1.7 现有唯一的"断言"是手写的，不在框架内

这是理解改造范围的关键点。**主循环里没有任何断言能力**。现有的校验全部是在循环之外手写的 Python 函数，例如 `examples/flights.py:18`：

```python
def verify(page):
    """Independent checks on the resulting page, not the model's DONE answer."""
    ...
    checks = {
        "search_page": parsed.hostname == "www.google.com" and parsed.path == "/travel/flights/search",
        "one_way": values.get("Change ticket type. One way") == "One way",
        "origin": values.get("Where from?") == "Zürich",
        ...
    }
    return {"passed": all(checks.values()), "checks": checks, "visible_flights": flights}
```

`scripts/smoke.py:43-45` 是另一个例子，直接写死：

```python
assert state["status"] == "done"
assert state["page"]["url"].endswith("#casa-flora")
assert "Your filters: Design · Free cancellation enabled · Destination Lisbon" in state["verification_text"]
```

**这两个文件就是"测试框架"的雏形**：给定一句自然语言目标 → 跑 → 断言最终页面。改造的本质，就是**把这两个文件里手写的断言，换成用户用自然语言声明的预期结果**。

### 1.8 已经确立的工程契约（改造必须继承）

`AGENTS.md` 里的这些规则不是风格偏好，而是安全边界，改造时不应违反：

| 规则 | 对改造的含义 |
|---|---|
| 输入是一个自然语言目标，不得加入站点专用计划或硬编码字段值 | 用例文件不能退化成"写死的步骤脚本" |
| 目标必须映射到已观测元素和受支持操作；**绝不让模型输出选择器或可执行代码** | 断言层也不能引入代码生成 |
| 不重试浏览器变更操作 | pytest 层的"失败重试"只能在**用例级**重跑，不能做成步骤级重试 |
| 截图可选，模型不消费截图 | 截图只喂 Allure，不进模型上下文 |
| 独立验证最终结果；**DONE 不是成功的证明** | 断言必须是独立的第二次判定，不能复用 DONE |
| 测试不得调用付费 API | 单测必须离线；真实调用只放在显式标记的用例里 |

`★ Insight ─────────────────────────────────────`
**发现一个值得修的配置问题**：`.env` 设了 `TEXT_MODEL_REASONING=none`，`model.py:167` 据此发送 `{"reasoning": {"enabled": false}}`。但该阿里云百炼兼容端点**不认这个字段**——实测推理 token 仍占 31/39。

对比实测（同一个 prompt，`max_tokens=1024`）：

| 参数写法 | 推理 token | 耗时 |
|---|---|---|
| `reasoning: {enabled: false}`（**当前行为**） | 31/39 | **2771 ms** |
| 不发任何 reasoning 字段 | 23/31 | 6044 ms |
| `reasoning: {effort: low}` | 23/31 | 2941 ms |
| **`enable_thinking: false`** | **0/7** | **1837 ms** |
| **`thinking: {type: disabled}`** | **0/7** | **2061 ms** |

后两种写法能真正关掉思考，**省下约 900 ms 且消除"推理吃光 token 导致空输出"的风险**——我第一次探针用 `max_tokens=256` 时，模型把 256 个 token 全用在推理上，`content` 返回空串，实际业务里这会表现为"填写字段失败"。建议改成按 base_url 分派三种写法。
`─────────────────────────────────────────────────`

### 3.8 `noul` / `score`：断言层的原生解（本次最重要的发现）

**现状：当前代码只用了 `choice` 一种问题类型。** TypeSafe 实际支持三种，且能**在同一请求里混用**：

| 类型 | 用途 | 返回 |
|---|---|---|
| `choice` | 从候选里选一个（当前的 操作/目标 决策） | `choice` + `probabilities` + `confidence` |
| `score` | 按评分标准打分 | `score` + 每档概率 + `confidence` + `legend` |
| **`noul`** | **对一个陈述做真值判断** | **`noul`: 0–1 概率** |

实测：**一次请求**同时拿到 操作决策 + 三条中文断言 + 一条评分：

```
HTTP 200 in 1711 ms（一次往返）
  operation        : choice  → "DONE"  (0.95)
  click_target     : choice  → "1"     (1.00)
  断言_目的地       : noul    → 0.97
  断言_详情页       : noul    → 0.96
  断言_免费取消     : noul    → 0.97
  需求覆盖度        : score   → 2.96 / 3  (confidence 0.96, P(3)=0.97)
  usage: {"input_tokens": 830, "output_tokens": 144}
```

**这意味着断言层可以复用同一个模型、同一次请求，不需要外挂一个"大模型裁判"。** 官方文档也把 `noul` 用于 self-consistency、citation double-checking、LLM guardrails 等场景。

`★ Insight ─────────────────────────────────────`
**但这里有一个必须正面处理的设计张力**：用**同一个模型**既"开车"又"判分"，会不会自己给自己打分？

拆开看，风险比想象的小：`noul` 问的是**"页面状态是否满足这个陈述"**，是一个**关于页面的事实判断**，而不是"我刚才做得对不对"。模型没有自己的动作记忆，它只看得到当前状态，所以这本质上是**同权重体系的系统性盲点**，而不是"护短"。

不过 `AGENTS.md` 那句"**DONE 不是成功的证明**"仍然完全适用。所以推荐**混合断言**：
- `noul` 负责**语义预期**（"页面上显示启用了免费取消"）——这是手写断言做不到的部分；
- 对**可机械判定**的东西（URL、元素值、条目数、字段是否可编辑），继续用现有的确定性 Python 断言（`flights.py::verify` 那套），零成本、零抖动、零幻觉。
`─────────────────────────────────────────────────`

### 3.9 用例隔离（实测可行）

**问题**：`Browser.__init__`（`browser.py:23`）直接 `Target.createTarget`，落在 Chrome 的**默认上下文**。所有用例共用 cookie / localStorage / 缓存 → 用例之间会互相污染。

**实测结论**：`browser_harness.cdp()` 是**通用 CDP 透传**（`helpers.py:72` 签名 `cdp(method, session_id=None, **params)`），所以 `Target.createBrowserContext` 直接可调，**不需要修改或替换该依赖**：

```
1. Target.getBrowserContexts      → {'browserContextIds': [], 'defaultBrowserContextId': '383AA…'}
2. Target.createBrowserContext    → '7EC5704D…'
3. Target.createTarget(browserContextId='7EC5704D…') → 成功
4. 在该上下文写入 cookie + localStorage → 读回 ['jev_probe=secret', 'secret']
5. 默认上下文访问【同一源】         → 读回 ['', None]      ← 隔离生效，无泄漏
6. Target.disposeBrowserContext   → 剩余上下文数回到 0     ← 清理干净
```

**改造量**：`Browser.__init__` 增加 `Target.createBrowserContext` 并把 `browserContextId` 传给 `createTarget`；`close()` 增加 `disposeBrowserContext`。约 **8 行**。

### 4.3 风险与限制（诚实清单）

**🔴 高风险——必须在立项后第一周验证**

1. **真实目标系统的控件复杂度**。README 明确列出不支持的范围：**Shadow DOM、iframe、canvas、上传、弹窗新标签、嵌套滚动、任意键盘控件**。企业级 UI（E9 workspace 这类系统通常大量使用 iframe、复杂表格/树、自定义控件）很可能**直接命中这些边界**。
   **必须做的第一件事**：拿 3–5 条真实的 E9 用例做探针，统计"因不支持的操作类型而卡住"的比例。**这个数字决定整个一期改造的价值。**
   > **【2026-09-23 已实测修正】** 探针结论：**不是 iframe，是元素发现**。E9 用 `<div>` + `[ecid]` + JS 事件委托承载交互元素，`snapshot.js` 只认原生控件/ARIA，实测 **19 个 E9 风格元素只发现 1 个**。执行路径（CDP 鼠标事件）对这类元素**有效**（3/3 点击产生真实 DOM 变化）。所以投入方向从"补 frame 遍历"改为"**扩展 `snapshot.js` 的元素发现范围**"，工作量小得多。详见 [一期改造实施方案.md](./一期改造实施方案.md) §6.5–6.7。

2. **端到端验证只在本地 fixture 上完成**。本报告的复杂度上限就是 fixture.html（一个静态表单页）。真实系统页面更大 → 元素更多 → 250 个候选动作的上限可能截断目标元素（`snapshot.js:99`）→ 决策失败。

**🟡 中风险**

3. **成本与延迟随页面大小增长**。本项目 fixture 每次决策约 2,841 输入 token；Google Flights 场景实测约 5,326 token/次（`docs/performance.md`）。页面文本上限 6000 字符、候选动作上限 250，构成了上界，但**大页面单条用例的 token 成本可能是 fixture 的数倍**。TypeSafe 未公开定价，建议**先跑 20 条真实用例测出成本基线**再定规模。

4. **重跑策略与"不重试"原则冲突**。`AGENTS.md` 规定"绝不重试浏览器变更操作"。测试框架通常需要失败重试。**只能在用例级重跑**（pytest `--reruns` 语义），不能做步骤级重试，否则可能重复提交/重复下单。这是**策略决定，需要明确写进框架契约**。

5. **断言阈值需要标定**。实测真值 0.97 / 假值 0.01 判别清晰，但模糊断言实测会落到 **0.53**。建议：默认阈值 0.5，**并把原始 `noul` 概率写进 Allure 报告**供人工审计；对关键断言强制要求写得更原子。

6. **`noul` 判定的系统性盲点**。同一模型的语义盲区在"驾驶"和"断言"两侧同时存在。缓解：关键用例保留确定性断言（URL / 元素值 / 计数）。

**🟢 低风险 / 可延后**

7. **并行执行**。`ensure_daemon()` 是进程级单例，所有 worker 共用同一个 Chrome。上下文隔离能解决 cookie 污染，但**渲染与调度仍集中在一个浏览器**。一期建议**串行执行**；若要并行，需要按 worker 分 daemon（`BU_NAME`）或分浏览器（`BU_CDP_URL`）。

8. **`MAX_STEPS=60` / 决策预算 120**（`questions.py:26`, `agent.py:75`）。长流程用例可能撞上限，建议做成可按用例覆盖。

9. **单次模型调用的网络抖动**。第一次 TypeSafe 调用 1714 ms / 首次 e2e 中 1337 ms，后续降到 ~336–454 ms。冷启动延迟要计入超时设置。

### 5.3 断言层设计（关键决策）

调用方只需知道：`verify(page, expectations) -> {"passed": bool, "evidence": {...}}`

实现时，下面这个函数是整个断言层的核心。**它的实现方式直接决定了框架的可信度**，而这里有真实的取舍：

```python
# jev_ultrafast/verify.py  —— 请实现这个函数

def judge(page, expectations, *, threshold=0.5, model=...):
    """把自然语言预期判定为通过/不通过。

    expectations: list[str]，每条是一个原子的自然语言陈述，如
        ["搜索的目的地是里斯本", "已启用免费取消筛选"]

    返回: {"passed": bool, "results": [{"claim":..., "noul":..., "passed":...}], "usage": {...}}

    需要你来定的取舍：
    1) 用 noul 还是 score？noul 给 0-1 概率、实现简单；
       score 能表达"部分满足"但需要为每条断言写评分标准。
    2) 阈值定多少？实测真值 0.97、假值 0.01，但模糊断言会落到 0.53。
    3) 多条断言如何合成总分？全部必须通过（AND），
       还是允许"3 条中满足 2 条"这种部分通过？
    4) 是否要与 DONE 决策同请求发出（省一次往返），
       还是独立发一次（判定更干净、不与被测行为耦合）？
    """
```

**我的建议**（供参考，不是唯一答案）：
- 用 `noul`，默认阈值 `0.5`，**并把原始概率写进 Allure**；
- 多条断言默认 **AND**（任一条不过即用例失败），但把每条的概率都记录下来，便于区分"彻底没做"和"做了一半"；
- **独立发一次请求**，不与 DONE 同请求——因为断言必须独立于被测行为，这与 `AGENTS.md` 的"独立验证最终结果"一致。
