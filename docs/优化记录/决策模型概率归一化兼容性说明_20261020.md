## 0. 结论摘要

1. **单个概率值都在 `[0, 1]` 内**——18 个问题、全部候选值，没有一个越界；**选中项也全部是最大概率项**。
2. 问题不是"概率越界"，而是**概率之和不等于 1**：实测 18 个问题里 7 个偏离超过 2%，范围 `0.97 ~ 1.01`。
3. 偏差**随候选数量增大而增大**：1–6 个候选平均和 `0.9980`，21–100 个候选平均和 `0.9800`。这与"两位小数四舍五入误差累计"的解释一致。
4. 框架 `validate_choice` 要求 `|sum - 1| < 0.02`，因此 38 个候选的大题会被整条拒收。
5. **真实 E9 用例验证**：同一用例、同一环境下，Jev `4/4` 通过，阿里 `3/4` 通过；失败项是语义断言（`noul=0.54/0.55` vs 阈值 `0.75`），不是导航错误。
6. 如果未来要做归一化，**推荐在客户端校验前做等比缩放**；它对 Jev 是幂等 no-op，对任何端点都适用，但必须把"原始概率和"留在报告里，避免静默修正。

## 1. 背景

框架把"决策"抽象成 TypeSafe System One 契约：一次请求同时问"做什么操作"和"对哪个目标"，
响应里每个问题返回：

```json
{
  "choice": "25",
  "confidence": 0.65,
  "probabilities": {"1": 0.02, "...": "...", "25": 0.66}
}
```

`model.validate_choice()` 对每个问题做五条硬校验：

```python
answer["choice"] in ids                                  # ① 选中项在候选集内
set(probabilities) == set(ids)                           # ② 概率键与候选集完全一致
all(0 <= n <= 1 for n in numbers)                        # ③ 概率与 confidence 都在 [0,1]
abs(sum(probabilities.values()) - 1) < 0.02              # ④ 概率和必须约等于 1
probabilities[answer["choice"]] >= max(probabilities)    # ⑤ 选中项必须是最大
```

阿里云百炼的 `decision-model-preview` 明确实现了 `POST /v1/systemone`，但实测会在 ④ 上失败。

### 2.3 结论

**"概率值不是 0–1"这个说法不准确。** 准确表述是：

> 阿里 `decision-model-preview` 返回的**每个概率值都在 `[0,1]` 内**，
> 但**同一问题的概率总和没有归一到 1**，且偏差随候选数增大。

这解释了为什么小规模请求（3 个候选）看起来完全正常（`0.97+0.02+0.01=1.00`），
而 38 个候选的大题会累计出 3% 的缺口。

作为对照，Jev（经 OpenRouter）同类请求的 112 个问题：

- 概率和范围 `0.99 ~ 1.00`
- 偏离超过 2% 的问题：**0 个**

## 3. 框架为什么拒收

### 3.1 失败点在 ④，不在 ①②③⑤

以本次捕获的失败响应为例（38 个候选）：

- `choice = "25"`，在候选集内 → ① 通过
- 概率键与 `criteria` 键完全一致（38 个） → ② 通过
- 所有值都在 `[0,1]` → ③ 通过
- `probabilities["25"] = 0.66`，就是最大值 → ⑤ 通过
- `sum = 0.97`，`|0.97 - 1| = 0.03 >= 0.02` → **④ 失败**

框架报错：

```
ValueError: Invalid TypeSafe response; no action executed.
```

### 3.2 为什么是稳定失败

`DECISION_ATTEMPTS = 2` 会重发一次，但服务端对同一请求返回逐位相同的概率（实测重跑两个进程结果一致），
所以重发不会自愈。用户侧表现为"第一次决策就死"。

### 3.3 与候选数的关系

| 候选数区间 | 问题数 | 平均概率和 |
|---|---:|---:|
| 1–6 | 10 | 0.9980 |
| 21–100 | 8 | 0.9800 |

两位小数的情况下，每个概率最多有 `±0.005` 的舍入误差；候选越多，累计偏差越明显。
实测偏差量级（最多 0.03）小于"候选数 × 0.005"的理论上界（38 × 0.005 = 0.19），
说明服务端可能做过某种近似处理，但**没有做最后的归一化校正**。

## 4. 真实 E9 用例验证（2026-10-20）

### 4.1 环境与用例

- 环境：`config.json` 里配置的 E9 测试环境（`base_url`）
- 账号：管理员账号与若干自动化账号，登录均成功
- 用例：`cases/e9/workflow_design.yaml::e9-wf-designer-reach`
  - 以管理员进入 `/wui/engine.html#/workflowengine/path/pathSet/pathList`
  - goal 明确要求"到达列表页后停止，不要点击任何按钮"
  - 4 条断言：URL、文本「路径设置」、文本「路径名称」、语义断言（noul）

### 4.2 结果对比

| 指标 | 阿里 `decision-model-preview` | Jev（OpenRouter） |
|---|---|---|
| 用例结果 | **3/4 断言通过 → failed** | **4/4 通过 → passed** |
| 决策次数 | 2 次（pytest 重跑两轮，每轮 1 次） | 1 次 |
| 决策选择 | DONE | DONE |
| DONE 置信度 | **0.28 / 0.31** | **0.71** |
| 决策端到端耗时 | 574 / 592 ms | 2034 ms |
| 输入 token | 6,944 | 10,381 |
| URL 断言 | ✅ | ✅ |
| 文本「路径设置」 | ✅ | ✅ |
| 文本「路径名称」 | ✅ | ✅ |
| 语义断言 `noul` | **0.54 / 0.55（阈值 0.75）→ 失败** | **0.90 → 通过** |
| 语义断言耗时 | 228 ms | —（见报告） |

**解读：**

1. 阿里的**决策链路是通的**：它正确判断了"页面已满足 goal，应当 DONE"，没有乱点。
2. 失败发生在**语义断言**（`judge`，同一个决策模型）：它对"页面上显示的是流程（路径）名称列表，
   并带有新增流程的按钮"只给出 `noul=0.54`，低于框架阈值 `0.75`；而 URL 和两条文本断言都证明页面是对的。
3. 这说明该模型在**中文页面的语义判断上偏保守**，而不是导航能力不行。
4. 本次阿里没有触发概率和校验失败——因为两次决策都只问 `operation`（6 个候选），
   和恰好为 `1.00`。这再次印证：**失败只在大候选集上出现**。

### 4.3 速度对比（同一用例）

- 阿里单次决策：**574–592 ms**
- Jev 单次决策：**2034 ms**
- 阿里快约 **3.5 倍**

> ⚠️ 本次每条路径只有 1–2 次决策，样本极小，不能当作稳定结论。
> 上一轮公开站点 demo 的 8 vs 40 次决策样本测得：阿里中位 278 ms、Jev 中位 669 ms（约 2.4 倍）。
> 两轮的方向一致，但具体倍数会随页面规模与候选数变化。

## 5. 归一化方案设计（已实施）

### 5.1 目标

- 让"概率未归一"不再把一条合法决策整条拒收；
- **不改变** Jev 的行为（它本来就归一）；
- **不改变** choice 的选择结果与相对排序；
- 修正动作必须在报告里**可见**，不能静默抹平。

### 5.2 放置位置

推荐放在 `model._decision_once()` 调用 `validate_choice()` **之前**，
对 `post_json()` 返回的 `result["answers"]` 做一次统一处理：

```
post_json() → normalize_answers() → validate_choice() → choose()
```

理由：

- 位置集中：所有决策题（operation / *_target）都经过同一个函数；
- `judge.py` 的语义断言不走 `validate_choice`，不会被误改；
- 不改 `post_json()` 的传输语义（重试、超时、错误分类保持原样）。

### 5.3 算法

```python
#: 与 validate_choice 共用同一个阈值——两处各写一个数会漂移。
PROBABILITY_SUM_TOLERANCE = 0.02

def normalize_probabilities(answers):
    """把每个 choice 题的概率等比缩放到和为 1；返回原始概率和（留痕用）。"""
    raw_sums = {}
    for name, answer in answers.items():
        probabilities = answer.get("probabilities")
        if not isinstance(probabilities, dict) or not probabilities:
            continue
        total = sum(probabilities.values())
        raw_sums[name] = round(total, 6)
        if not math.isfinite(total) or total <= 0:
            continue                      # 交给 validate_choice 拒绝，不掩盖坏数据
        if abs(total - 1) < PROBABILITY_SUM_TOLERANCE:
            continue                      # 校验本来就能过，逐位不变（对 Jev 是 no-op）
        for key in probabilities:
            probabilities[key] = probabilities[key] / total
    return raw_sums
```

> 实施时把"是否跳过"的判据从 `1e-9` 改成了**校验阈值本身（0.02）**：
> 这样 Jev 实测的 `0.99` 响应会逐位保持不变，只有**本来就会被拒收**的响应才被修正。

关键性质：

| 性质 | 说明 |
|---|---|
| **等比缩放** | 只除以同一个 `total`，相对排序不变 |
| **不改 choice** | `choice` 字段原样保留 |
| **不改 confidence** | confidence 是独立标量，校验只要求 `[0,1]` |
| **幂等** | 已归一的响应不会被二次缩放 |
| **坏数据不掩盖** | `total <= 0` / 非有限值时不归一，仍由校验拒绝 |
| **不含 `type` 判断** | 只处理有 `probabilities` 的问题，`noul` 等无概率字段的响应不受影响 |

### 5.4 不同模型如何兼容

归一化是**端点无关的通用后处理**，因此不需要为每个厂商写分支。兼容性矩阵：

| 模型 / 端点 | 典型概率和 | 归一化后行为 | 是否需要 |
|---|---:|---|---|
| TypeSafe 官方 Jev | `1.00` | no-op（逐位不变） | 不需要，但无副作用 |
| OpenRouter Jev | `0.99–1.00` | 通常 no-op；偏差 > 容差时轻微缩放 | 兼容 |
| 阿里 `decision-model-preview` | `0.97–1.01` | 缩放到 1 | **需要** |
| StartLux（本地部署） | 未实测 | 按同一规则 | 兼容 |
| 其他兼容 System One 的服务 | 未实测 | 按同一规则 | 兼容 |

**为什么统一生效、而不是"只对自定义端点生效"：**

- 只对自定义端点生效会让校验规则因端点而异，报告和测试都难以解释；
- 统一生效对 Jev 是 no-op，实测不改变它的任何数值；
- 统一生效的代价是：**未来若某个模型故意返回不归一概率**（例如用"概率和<1"表达不确定），
  该信号会被抹掉。当前 TypeSafe 契约没有这种语义，风险可接受，但应在文档中写明。

### 5.5 可观测性（已实施）

归一化会让问题"看起来消失"，所以必须在报告里留下原始事实。决策记录中增加：

```json
{
  "probability_normalized": true,
  "raw_probability_sums": {"operation": 0.99, "click_target": 0.97}
}
```

并在 Allure 的决策附件里展示。这样：

- 排查时能区分"模型正常"与"被框架修正过"；
- 若某个端点突然开始返回不归一概率，能第一时间看到趋势；
- 与项目既有原则一致——**重发要看得见，修正也要看得见**（参见 `DECISION_ATTEMPTS` 注释）。

### 5.6 可选开关（第一期未上）

| 取值 | 行为 | 适用 |
|---|---|---|
| `auto`（建议默认） | 偏离超过容差才归一，并记录 | 兼容多模型 |
| `strict` | 保持现状，不归一，超阈值即拒收 | 仅用 Jev 时 |
| `off` | 不归一，也不记录 | 调试用 |

对应环境变量：`DECISION_MODEL_NORMALIZE=auto|strict|off`（默认 `auto`）。
**第一期先不上开关**，固定 `auto` + 记录原始和，减少配置面；等出现第二个需要 `strict` 的模型再加。

### 5.7 风险与代价

| 风险 | 评估 |
|---|---|
| 掩盖服务端 bug | 中。通过 `raw_probability_sums` 记录缓解；可加告警（连续 N 次偏离 > 阈值时在报告里标红） |
| 概率绝对值的校准意义被轻微放大 | 低。缩放后每个候选被放大 `1/total`（38 候选约 3%），排序不变 |
| 选中项不是最大时仍会被拒 | 是，⑤ 不变；归一化不改变这一保护 |
| 对 Jev 产生意外影响 | 实测无：Jev 的 `sum≈1`，`abs(sum-1) < 0.02` 时跳过 |
| 测试复杂度 | 低。可完全离线覆盖（构造不归一响应） |

## 6. 替代方案对比

| 方案 | 做法 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| **A. 框架层归一化** | 校验前等比缩放 | 一处改动、对所有模型生效、Jev no-op | 需修改框架；会掩盖服务端问题（可用记录缓解） | **推荐** |
| B. 服务端修复 | 让阿里在返回前归一 | 最干净、不碰框架 | 依赖厂商排期，不可控 | 并行反馈 |
| C. 网关/代理归一化 | 在请求链路中放一层代理改响应 | 不改框架 | 多一个部署件、排障面变大 | 不推荐 |
| D. 放宽阈值到 0.05 | 改 `0.02` | 一行改动 | **弱化校验**，会让更多坏响应通过；违反项目"不得弱化断言"原则 | 不推荐 |
| E. 换模型 | 用 Jev / StartLux | 无兼容问题 | 失去阿里模型的速度与成本优势 | 视业务取舍 |

## 7. 测试计划（已实施）

1. **离线单测**（`tests/test_decision_model_normalization.py`）：
   - 不归一响应（和为 0.97）→ 归一化后通过校验；
   - 已归一响应（和为 1.00）→ **逐位不变**（对 Jev 的 no-op 保证）；
   - 和为 0 / 负数 / 非数值 → 不归一，仍被拒收；
   - 选中项不是最大 → 归一化后仍被拒收；
   - `raw_probability_sums` / `probability_normalized` 被正确记录。
2. **真机验证**：
   - 阿里模型跑 `e9-wf-designer-reach`，期望 4/4；
   - Jev 跑同一用例，期望 4/4 且数值与改造前一致；
   - 对比两轮的决策附件，确认 `raw_probability_sums` 可见。
3. **回归**：`uv run pytest`（UI 域全部离线测试）。
